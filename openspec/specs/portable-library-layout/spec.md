# portable-library-layout Specification

## Purpose

为 Echo 定义可携带、可版本化的资料库布局，使媒体与逻辑资料在不同设备上可被独立恢复，同时不把本机数据库或敏感配置作为资料库内容传播。

## Requirements

### Requirement: 受管理资料库目录布局

系统 MUST 使用以下资料库目录布局：

```text
<library-root>/
├── media/
│   └── <artist>/<artist> - <title>.<extension>
└── echo/
    ├── manifest.json
    ├── records/
    │   ├── songs/<uuid-prefix>/<song-uuid>.json
    │   ├── playlists/<uuid-prefix>/<playlist-uuid>.json
    │   ├── playlist-items/<uuid-prefix>/<item-uuid>.json
    │   ├── favorites/<uuid-prefix>/<song-uuid>.json
    │   ├── overrides/<uuid-prefix>/<song-uuid>.json
    │   ├── play-stats/<uuid-prefix>/<song-uuid>.json
    │   └── tombstones/<object-kind>/<uuid-prefix>/<object-uuid>.json
    ├── assets/<content-hash>
    ├── transactions/<operation-id>/
    ├── state/
    ├── migrations/<migration-id>/
    ├── media/<declared-managed-version>/
    ├── snapshot.json
    └── tmp/<operation-id>/
```

系统 MUST 将 Echo 管理导入的音频及同名 `.lrc` 置于 `media/` 下；现有同步发布的不可变受管版本允许在经过持久声明、owner/version 与哈希校验的 `echo/media/` 中保留。该例外 MUST NOT 使任意 `echo/` 文件成为普通扫描或歌曲逻辑路径。`echo/` 是资料库控制面；`echo/tmp/` 仅为未提交资源的本机暂存，不作为音乐列表或普通媒体浏览入口。

布局 MUST 覆盖每种对象、用户资源原件以及丢失 SQLite 后仍必需的提交/候选/迁移恢复资料。恢复凭据 MUST NOT 仅位于 `echo/tmp/` 或应用数据库。墓碑 MUST 按删除对象类型隔离，防止共享 UUID 的不同对象互相覆盖。目录私有恢复资料不得原样作为同步传输资料。

#### Scenario: 新资料库导入一首歌曲
- **WHEN** 用户向一个可写的新资料库导入带有艺人和标题的音频
- **THEN** 音频被发布到 `media/<安全艺人>/<安全艺人> - <安全标题>.<扩展名>`，同名歌词若成功导入则位于相同目录和基础名，控制面与暂存内容不出现在曲库

#### Scenario: 控制面目录不可写
- **WHEN** 资料库媒体根可读但 `echo/` 无法安全创建或更新
- **THEN** 系统不得启用导入、逻辑变更或同步入站写入，并明确报告控制面不可用；已有已提交可读媒体仍可按只读资料库语义浏览

#### Scenario: 每种对象种类都有对应目录
- **WHEN** 系统写出歌曲、歌单、成员、收藏、覆盖层、播放统计或墓碑
- **THEN** 每种对象均有对应分片记录，墓碑按对象类型分隔，没有任一种类因布局缺失而被静默丢弃

#### Scenario: 完整备份包括恢复必需资料
- **WHEN** 用户在稳定提交边界备份完整音乐库
- **THEN** 备份包含 `media/`、对象、用户资源、仍需重放的目录提交/候选/迁移凭据及被引用的受管版本，不把 `snapshot.json` 或应用缓存作为唯一恢复依据
### Requirement: 可携带对象资料

`echo/` MUST 含有版本化 manifest 和以稳定 UUID 分片存放的对象资料。对象 MUST 覆盖歌曲、收藏、歌单定义、成员及顺序、覆盖层、逐设备播放统计和类型化墓碑；歌曲 MUST 包含资料库逻辑 ID、BLAKE3 内容哈希、原入库时刻与规范化逻辑相对路径。新导入媒体 MUST 使用 `media/`；已有媒体在其他安全根相对子目录时仍可按既有同步声明处理。逻辑媒体路径不得为绝对路径、越界路径或任意 `echo/` 控制路径；受管理不可变版本的实际位置通过独立可校验声明恢复，不冒充逻辑路径。

每一次已提交用户变更（包括删除、取消喜欢和空歌单）MUST 先可靠提交到音乐库目录，再更新 SQLite；不得把对象记录写入作为 SQLite 提交后的可忽略副作用。记录 MUST 保存稳定身份、关系、已知创建/加入时间和全部已支持的用户编辑值；自定义封面/歌词资源 MUST 有资料库内可校验原件及引用，不能只存应用缓存 key。支持的历史格式缺失字段应兼容读取且不得伪造时间；该读取兼容不要求回填或改写旧记录。

播放统计 MUST 按设备单调桶表达并可幂等合并，不能用 LWW 总计覆盖另一设备。逐设备桶与重放所需的幂等播放事件身份 MUST 分开承载：共享对象只保存设备桶，事件身份属于目录私有 state（`echo/state/playback-events/`），MUST NOT 进入共享/同步载荷或成为播放会话状态。confirmed baseline 的完整 payload 与本地 pending 意图 MUST 分开表达，不得把带旧确认版本的新本地值当作已确认。必需的 typed alias、墓碑与候选关系 MUST 可随完整目录恢复。

对象及恢复资料 MUST NOT 包含 SQLite 文件、端点、凭据或本机绝对路径；共享对象不包含偏好、设备缓存或播放会话。网络共享 MUST 覆盖 manifest 所表达的兼容信息、已提交对象与被引用的资源，排除 tmp、目录私有事务/候选/迁移日志；`snapshot.json` 只能作为可再生加速文件。恢复所需本机资料随完整目录备份保留，但不因此成为共享 DTO。

#### Scenario: 检查资料库控制面
- **WHEN** 支持同步的设备读取兼容的 `echo/` 资料
- **THEN** 它可识别库 ID、格式、各对象 UUID、版本、业务载荷与必要资源引用，无需读取另一设备 SQLite

#### Scenario: 路径数据被序列化
- **WHEN** 已导入歌曲的对象资料被生成或更新
- **THEN** 保存规范化的逻辑相对路径及可校验资源声明，不包含盘符、主目录、数据库位置或认证信息

#### Scenario: 同步忽略临时目录
- **WHEN** 导入或接收正在暂存资源或重放本机目录提交
- **THEN** 网络不传输 tmp 或私有事务日志，只从已恢复的一致已提交对象及授权资源导出，不暴露部分提交

#### Scenario: 歌单与成员的变更被材料化
- **WHEN** 用户成功创建、重命名、删除歌单或添加/移除成员
- **THEN** 目录先保存完整定义、成员身份与顺序或相应墓碑，清除 SQLite 后恢复同一歌单和有效成员，空歌单也不丢失

#### Scenario: 播放统计随资料库移动
- **WHEN** 一次完整播放被报告为统计已保存
- **THEN** 目录已保存对应设备桶与幂等事件事实，重建/重放不重复加计，不含本机路径或播放会话细节

#### Scenario: 取消收藏不留下悬空记录
- **WHEN** 用户成功取消一首歌的「我的喜欢」
- **THEN** 目录已提交 false 状态或合法类型化墓碑，重建不会被旧 true 记录重新加入喜欢

#### Scenario: 播放统计幂等身份不进入共享载荷
- **WHEN** 一次已保存的播放事件被同步导出，或另一设备读取该歌曲的统计对象
- **THEN** 共享载荷只含逐设备桶与版本信息，不含播放会话标识或事件身份；重放所需的幂等事实仅存在于本机目录 state

#### Scenario: 封面资源原件随歌单恢复
- **WHEN** 用户成功设置歌单封面后应用缓存被清空
- **THEN** 系统从资料库的原件与对象引用恢复封面并重建缩略图，不能把失效缓存引用计为完整恢复
### Requirement: 歌曲入库时刻随资料库对象资料携带

系统 MUST 在新建或更新一首歌曲的可携带对象资料时，将该歌曲的入库时刻一并写入 `echo/records/songs/` 记录。入库时刻指歌曲被添加到当前资料库的那一时间点（墙钟毫秒），扫描发现的歌曲与用户主动导入的歌曲取值一致——都是“进入资料库”的时刻，而非文件本身的时间、元数据解析时间或任何后续变更时间。随对象资料写入的入库时刻必须与本机持久化的入库时刻一致，对该对象资料更新时不得因元数据、收藏或播放统计的变更而被改写。可携带对象资料仍 MUST NOT 包含绝对路径、SQLite 文件、同步端点、凭据、设备缓存或播放会话状态。

#### Scenario: 扫描发现新歌曲写入入库时刻
- **WHEN** 一次扫描在 `media/` 下首次发现并登记一首新歌曲，随后系统生成其可携带对象资料
- **THEN** 该对象资料携带一个入库时刻字段，其值与这次扫描把歌曲登记进本机资料库时记录的时间一致，且该字段与路径、内容哈希等既有字段一起序列化到 `echo/records/songs/` 下

#### Scenario: 手动导入歌曲写入入库时刻
- **WHEN** 用户把一首外部音频导入资料库，系统发布媒体并生成其可携带对象资料
- **THEN** 该对象资料携带的入库时刻与这次导入把歌曲登记进本机资料库的时间一致

#### Scenario: 入库时刻不被后续变更改写
- **WHEN** 一首已入库存放时间的歌曲此后被收藏、播放、编辑元数据，或再次扫描而内容不变
- **THEN** 这些变更生成的任何信息均不改变该歌曲可携带对象资料中的入库时刻，入库时刻始终等于其最初添加进资料库的时刻

### Requirement: 从资料库恢复或接续时还原歌曲入库时刻

系统 MUST 在从可携带对象资料重建本地歌曲时，把记录携带的入库时刻还原到本地，使恢复后的“最近添加”顺序与源库一致。这适用于两条路径：本机数据库被清除、应用重装或新设备从资料库恢复，以及打开一个已带有控制面的资料库目录时的接续投影。重建时 MUST 保留对象资料中的歌曲 UUID、入库时刻与媒体关联（UUID 优先），不得为入库时刻重新铸值或丢弃对象。对不携带入库时刻的历史对象记录（在本版本之前的写出的资料库），系统 MUST 仍能读取并按其既有语义恢复，不因缺该字段而丢弃记录、改变 UUID 或产生错误；此类记录恢复时不伪造入库时刻，保持与旧版本一致的兜底顺序。

#### Scenario: 本机数据库被清除后从资料库恢复保留最近添加顺序
- **WHEN** 本机应用数据目录被清除，用户重新选择此前使用过的同一资料库目录，系统从 `echo/` 对象资料投影到本地
- **THEN** 恢复后的每首歌曲其本地入库时刻与该资料库对象资料中记录的入库时刻一致，且“最近添加”视图的顺序与源库记录的顺序一致；对象数量与 UUID 与源库一致

#### Scenario: 新设备恢复时入库时刻随歌曲按原 UUID 还原
- **WHEN** 一台新设备取得一个含媒体与完整可携带对象资料的资料库并完成设置恢复
- **THEN** 歌曲以对象资料携带的 UUID 与入库时刻重建，“最近添加”顺序与源设备一致，且在媒体尚未就绪时该时间仍保留于不可用歌曲上

#### Scenario: 打开已有控制面的资料库目录时接续还原入库时刻
- **WHEN** 用户打开一个 `echo/` 中含对象资料、而本机数据库尚无对应记录的资料库目录（例如换设备或目录直接拷入），系统先做接续投影再扫描 `media/`
- **THEN** 投影的每首歌曲本地入库时刻等于其对象资料中记录的入库时刻，扫描 `media/` 关联媒体不会改写该入库时刻，也不会铸造新的 UUID

#### Scenario: 历史对象记录缺入库时刻仍可兼容恢复
- **WHEN** 系统读取一份不包含入库时刻字段的历史歌曲对象记录（本版本之前写出的资料库）
- **THEN** 该记录仍被正常读取并按既有语义恢复：歌曲 UUID、路径、内容哈希与元数据保持，入库时刻不伪造为虚假时间；“最近添加”顺序与该版本既有兜底行为一致，不产生错误、不丢弃歌曲

### Requirement: 新设备资料库重建

当用户在设置中选择同一资料库并连接其同步资料后，或者当用户重新打开一个已经具备可携带控制面的资料库目录时（包括卸载重装、清除本机应用数据目录，或把资料库目录从另一台机器拷入），系统 MUST 先验证 manifest 的资料库逻辑 ID 和格式兼容性，再将对象资料投影到本机数据库，并扫描 `media/` 关联文件。歌曲、收藏、歌单、歌单成员、覆盖层和播放统计 MUST 按原 UUID 恢复；对象资料存在但对应媒体尚未就绪时，系统 MUST 保留该对象并将歌曲标记为不可用，而不得分配替代 UUID 或丢弃歌单成员。重建 MUST 幂等：对同一目录重复执行不产生第二份对象，也不改变既有 UUID。

#### Scenario: 全新设备恢复完整资料
- **WHEN** 新设备取得一个含有媒体和完整可携带对象资料的资料库
- **THEN** 设置完成后，该设备重建与原设备一致的歌曲 UUID、我的喜欢、歌单、歌单成员顺序与播放统计，并可通过相对路径播放已校验媒体

#### Scenario: 同步资料先于媒体到达
- **WHEN** 新设备已获得歌曲、收藏和歌单对象资料，但 `media/` 中尚未存在某首歌曲
- **THEN** 系统显示该歌曲为不可用并保留所有 UUID 关联；媒体随后到达且哈希校验成功时恢复可用，不产生第二首歌曲

#### Scenario: 本机数据库丢失后重开同一资料库
- **WHEN** 本机应用数据目录被清除或应用被重装后，用户重新选择此前使用过的同一资料库目录
- **THEN** 系统按该目录的 `echo/` 对象资料恢复歌单、歌单成员顺序、「我的喜欢」与播放统计，歌曲 UUID 与该目录对象资料一致，且重新扫描 `media/` 不会产生新的 UUID

#### Scenario: 重复打开结果稳定
- **WHEN** 用户对同一资料库目录连续两次执行打开与重建
- **THEN** 对象数量、UUID、歌单成员顺序与播放统计与首次一致，不产生重复歌曲、重复歌单或重复成员

### Requirement: 控制面存在性与自愈

对一个被启用为受管资料库的可写目录，系统 MUST 保证 `echo/manifest.json` 存在，且其中记录资料库逻辑 ID 与格式版本。首次启用时 MUST 建立该 manifest；打开资料库发现 manifest 缺失但 `echo/records/` 已有对象资料时，系统 MUST 依据该目录既有对象资料自愈重建 manifest，并保留全部对象与 UUID，不得因此把该目录当作新资料库重新扫描并铸造新标识。当 `echo/` 无法安全创建或更新时，系统 MUST NOT 就地覆盖或删除既有控制面文件，MUST 明确报告控制面不可用，且 MUST NOT 静默把本机数据库当作唯一存储继续接受逻辑变更。

#### Scenario: 首次启用即建立 manifest
- **WHEN** 用户首次把一个可写目录启用为受管资料库并导入第一首歌
- **THEN** 该目录出现 `echo/manifest.json`，包含稳定的资料库逻辑 ID 与格式版本，后续写入的对象资料与该 manifest 位于同一 `echo/` 下

#### Scenario: manifest 缺失时自愈
- **WHEN** 一个已有 `echo/records/` 对象资料但没有 `echo/manifest.json` 的目录被重新打开
- **THEN** 系统建立与该目录既有对象资料一致的 manifest，保留全部对象资料与 UUID，并在本次打开中报告一次自愈；不因 manifest 缺失而重新铸造歌曲标识

#### Scenario: 控制面不可写时不破坏既有内容
- **WHEN** 资料库目录可读但 `echo/` 无法安全创建或更新
- **THEN** 系统保留既有控制面文件原样不动，把该资料库置于只读语义并明确报告控制面不可用，不把逻辑变更写进无法材料化它们的本机数据库

### Requirement: 对象资料接续与对账

激活目录并扫描 `media/` 之前，系统 MUST 验证格式、恢复新协议已提交目录操作，再解析可识别的 typed envelope、别名、墓碑、confirmed baseline 与 pending 意图，按已提交稳定 UUID 投影本机状态。读取受支持的旧格式时保留既有记录身份与关系表示，不因 SQLite 缺记录而改写旧记录或执行历史回填、身份修复、关系补全。缺少媒体 MUST 保留已提交歌曲及其关联，仅标记不可用；已声明不可变版本须校验实际资源位置，不依赖普通扫描控制目录。

新协议投影与扫描 MUST 幂等；墓碑不得因再次扫描复活。无法解析的引用、损坏记录和未知格式 MUST 保留原件并标记未解析，不得臆造父对象或改写历史身份/关系。Core 分层与验证遵守工程规范 §3–§5、§8–§9 及 `library-durability` LD-10。

#### Scenario: 打开资料库先接续再扫描
- **WHEN** 用户打开一个含新协议对象资料、而本机数据库尚无对应记录的资料库目录
- **THEN** 系统先按已提交对象资料投影歌曲、收藏、歌单、成员与播放统计，再扫描媒体；已由资料库对象拥有的媒体不会被当作新文件铸造替代 UUID

#### Scenario: 对象资料与媒体不一致
- **WHEN** 记录存在而媒体缺失，或 `media/` 存在没有记录的文件
- **THEN** 前者保留已提交对象及所有关联并标记不可用；后者仅在新协议可写且身份已可靠提交时登记新对象，重复打开不重复登记

#### Scenario: 墓碑优先于陈旧记录
- **WHEN** 同类型同身份同时有陈旧对象和有效较新最终墓碑
- **THEN** 有效视图不复活该对象，其他共享 UUID 的类型不被误删，可撤销本机意图不冒充最终墓碑

#### Scenario: 重复接续结果稳定
- **WHEN** 系统对同一新协议资料库目录重复执行接续、投影与扫描
- **THEN** 对象数量、UUID、歌单成员顺序与播放统计与首次一致，且不产生重复对象记录

#### Scenario: 较新的本机身份不被旧记录覆盖
- **WHEN** 兼容读取期间发现旧格式对象记录与本机现有记录指向同一文件但 UUID 不同
- **THEN** 系统不得自动合并或改写旧记录身份与关系；保留未解析/冲突状态并报告，普通兼容读取不执行历史身份修复

#### Scenario: 打开新协议资料库后投影再扫描
- **WHEN** 用户打开含新协议对象资料而本机数据库尚无对应行的目录
- **THEN** 系统先恢复已提交目录操作，再按原 UUID 投影歌曲、喜欢、歌单、成员与统计，随后扫描不会为已拥有媒体新建替代 UUID

#### Scenario: 读取支持的旧格式
- **WHEN** 用户打开含受支持旧格式对象资料的目录
- **THEN** 系统兼容读取其中可识别的身份、字段与关系，不回填 SQLite 独有资料、不修复历史身份或关系，也不改写原记录

#### Scenario: 重复投影结果稳定
- **WHEN** 对同一新协议目录重复恢复、投影与扫描
- **THEN** 对象数、UUID、成员顺序、设备桶和候选身份保持稳定，无重复对象、计数或同步回声

#### Scenario: 未解析引用保持原样
- **WHEN** 新协议目录记录引用了无法验证的身份或缺失父对象
- **THEN** 系统保留原记录及关系并标记未解析，不合并身份、不推测父对象、不宣称历史关系已修复；旧格式兼容读取也不改写原记录
