# portable-library-layout Specification

## Purpose

为 Echo 定义可携带、可版本化的资料库布局，使媒体与逻辑资料在不同设备上可被独立恢复，同时不把本机数据库或敏感配置作为资料库内容传播。

## Requirements

### Requirement: 受管理资料库目录布局

系统 MUST 使用以下资料库目录布局：

```text
<library-root>/
├── media/
│   └── <artist>/<artist> - <title>.<extension>
└── echo/
    ├── manifest.json
    ├── records/
    │   ├── songs/<uuid-prefix>/<song-uuid>.json
    │   ├── playlists/<uuid-prefix>/<playlist-uuid>.json
    │   ├── playlist-items/<uuid-prefix>/<item-uuid>.json
    │   ├── favorites/<uuid-prefix>/<song-uuid>.json
    │   ├── overrides/<uuid-prefix>/<song-uuid>.json
    │   ├── play-stats/<uuid-prefix>/<song-uuid>.json
    │   └── tombstones/<uuid-prefix>/<object-uuid>.json
    ├── snapshot.json
    └── tmp/<operation-id>/
```

系统 MUST 将 Echo 管理导入的媒体置于资料库根目录的 `media/` 下；音频及其同名 `.lrc` 侧车只能位于该树。`echo/` 是可见的资料库控制面目录，`echo/tmp/` 是仅本机导入恢复临时目录；扫描、媒体浏览与用户可见的歌曲列表均不得把 `echo/` 内的文件当作音乐文件。

该布局 MUST 覆盖系统会写出的每一种对象种类；对象种类到目录名的映射 MUST 与布局一一对应，且不得存在「因为布局未列出该种类而静默丢弃对象资料」的写入路径。

#### Scenario: 新资料库导入一首歌曲
- **WHEN** 用户向一个可写的新资料库导入带有艺人和标题的音频
- **THEN** 音频被发布到 `media/<安全艺人>/<安全艺人> - <安全标题>.<扩展名>`，同名歌词若成功导入则位于相同目录和基础名，控制面与暂存内容不出现在曲库

#### Scenario: 控制面目录不可写
- **WHEN** 资料库媒体根可读但 `echo/` 无法安全创建或更新
- **THEN** 系统不得把该资料库作为可同步管理资料库启用导入或逻辑变更，并明确报告资料库控制面不可用；已有可读取媒体仍可按只读资料库语义浏览

#### Scenario: 每种对象种类都有对应目录
- **WHEN** 系统写出任一对象种类的可携带资料（歌曲、歌单、歌单成员、收藏、覆盖层、播放统计或墓碑）
- **THEN** 该记录位于 `echo/records/<该种类目录>/<uuid-prefix>/<对象-uuid>.json`，对象种类到目录名的映射与布局完全一致，且没有任何种类因缺少目录而被静默丢弃

### Requirement: 可携带对象资料

`echo/` MUST 含有版本化 manifest 和以稳定 UUID 分片存放的对象资料。对象资料 MUST 覆盖歌曲、收藏、歌单、歌单成员、覆盖层、播放统计及墓碑；歌曲资料 MUST 包含资料库逻辑 ID、BLAKE3 内容哈希与以 `media/` 开头的规范化相对路径。可携带对象资料不得包含绝对路径、SQLite 文件、同步端点、凭据、设备缓存或播放会话状态。同步资料 MUST 包含 `echo/manifest.json` 和 `echo/records/` 的已完成文件，MUST 排除 `echo/tmp/`，且 `snapshot.json` 只能作为可再生加速文件。

系统 MUST 保证本机数据库与对象资料之间没有单向的用户数据路径：每一次对上述对象的已提交变更（含删除）MUST 在同一变更流程内落入 `echo/records/` 或以墓碑取代旧记录。播放统计 MUST 以可加合并的形式表达——按设备分别记录计数，而不得使用单一「最后写入者获胜」计数器覆盖其他设备的播放次数。

#### Scenario: 检查资料库控制面
- **WHEN** 支持同步的设备读取 `echo/` 资料
- **THEN** 它可以识别资料库逻辑 ID、格式版本和每个对象的 UUID、版本及业务载荷，而无需读取另一台设备的 SQLite

#### Scenario: 路径数据被序列化
- **WHEN** 一首已导入歌曲的可携带资料被生成或更新
- **THEN** 该资料只包含类似 `media/周杰伦/周杰伦 - 晴天.flac` 的相对路径，不包含任一设备的盘符、主目录、数据库位置或认证信息

#### Scenario: 同步忽略临时目录
- **WHEN** 导入操作正在 `echo/tmp/<operation-id>/` 中暂存资源
- **THEN** 同步资料不包含该操作目录或任何暂存文件，恢复程序仅处理已完成的 manifest 与对象资料

#### Scenario: 歌单与成员的变更被材料化
- **WHEN** 用户创建、重命名或删除歌单，或向歌单添加/移除成员
- **THEN** `echo/records/playlists/` 与 `echo/records/playlist-items/` 随之写入新记录或以墓碑取代旧记录，使得本机数据库被清除后仍可据此恢复歌单及其成员顺序

#### Scenario: 播放统计随资料库移动
- **WHEN** 一首歌曲在本机被完整播放一次
- **THEN** `echo/records/play-stats/` 中该歌曲的记录被更新为包含本次播放的计数，载荷只含对象 UUID、版本、设备标识与计数，不含本机路径、数据库位置或播放会话状态

#### Scenario: 取消收藏不留下悬空记录
- **WHEN** 用户取消一首歌的「我的喜欢」
- **THEN** 该歌曲的可携带收藏资料被更新或由墓碑取代，使重新打开资料库时它不会重新出现在「我的喜欢」视图中

### Requirement: 歌曲入库时刻随资料库对象资料携带

系统 MUST 在新建或更新一首歌曲的可携带对象资料时，将该歌曲的入库时刻一并写入 `echo/records/songs/` 记录。入库时刻指歌曲被添加到当前资料库的那一时间点（墙钟毫秒），扫描发现的歌曲与用户主动导入的歌曲取值一致——都是“进入资料库”的时刻，而非文件本身的时间、元数据解析时间或任何后续变更时间。随对象资料写入的入库时刻必须与本机持久化的入库时刻一致，对该对象资料更新时不得因元数据、收藏或播放统计的变更而被改写。可携带对象资料仍 MUST NOT 包含绝对路径、SQLite 文件、同步端点、凭据、设备缓存或播放会话状态。

#### Scenario: 扫描发现新歌曲写入入库时刻
- **WHEN** 一次扫描在 `media/` 下首次发现并登记一首新歌曲，随后系统生成其可携带对象资料
- **THEN** 该对象资料携带一个入库时刻字段，其值与这次扫描把歌曲登记进本机资料库时记录的时间一致，且该字段与路径、内容哈希等既有字段一起序列化到 `echo/records/songs/` 下

#### Scenario: 手动导入歌曲写入入库时刻
- **WHEN** 用户把一首外部音频导入资料库，系统发布媒体并生成其可携带对象资料
- **THEN** 该对象资料携带的入库时刻与这次导入把歌曲登记进本机资料库的时间一致

#### Scenario: 入库时刻不被后续变更改写
- **WHEN** 一首已入库存放时间的歌曲此后被收藏、播放、编辑元数据，或再次扫描而内容不变
- **THEN** 这些变更生成的任何信息均不改变该歌曲可携带对象资料中的入库时刻，入库时刻始终等于其最初添加进资料库的时刻

### Requirement: 从资料库恢复或接续时还原歌曲入库时刻

系统 MUST 在从可携带对象资料重建本地歌曲时，把记录携带的入库时刻还原到本地，使恢复后的“最近添加”顺序与源库一致。这适用于两条路径：本机数据库被清除、应用重装或新设备从资料库恢复，以及打开一个已带有控制面的资料库目录时的接续投影。重建时 MUST 保留对象资料中的歌曲 UUID、入库时刻与媒体关联（UUID 优先），不得为入库时刻重新铸值或丢弃对象。对不携带入库时刻的历史对象记录（在本版本之前的写出的资料库），系统 MUST 仍能读取并按其既有语义恢复，不因缺该字段而丢弃记录、改变 UUID 或产生错误；此类记录恢复时不伪造入库时刻，保持与旧版本一致的兜底顺序。

#### Scenario: 本机数据库被清除后从资料库恢复保留最近添加顺序
- **WHEN** 本机应用数据目录被清除，用户重新选择此前使用过的同一资料库目录，系统从 `echo/` 对象资料投影到本地
- **THEN** 恢复后的每首歌曲其本地入库时刻与该资料库对象资料中记录的入库时刻一致，且“最近添加”视图的顺序与源库记录的顺序一致；对象数量与 UUID 与源库一致

#### Scenario: 新设备恢复时入库时刻随歌曲按原 UUID 还原
- **WHEN** 一台新设备取得一个含媒体与完整可携带对象资料的资料库并完成设置恢复
- **THEN** 歌曲以对象资料携带的 UUID 与入库时刻重建，“最近添加”顺序与源设备一致，且在媒体尚未就绪时该时间仍保留于不可用歌曲上

#### Scenario: 打开已有控制面的资料库目录时接续还原入库时刻
- **WHEN** 用户打开一个 `echo/` 中含对象资料、而本机数据库尚无对应记录的资料库目录（例如换设备或目录直接拷入），系统先做接续投影再扫描 `media/`
- **THEN** 投影的每首歌曲本地入库时刻等于其对象资料中记录的入库时刻，扫描 `media/` 关联媒体不会改写该入库时刻，也不会铸造新的 UUID

#### Scenario: 历史对象记录缺入库时刻仍可兼容恢复
- **WHEN** 系统读取一份不包含入库时刻字段的历史歌曲对象记录（本版本之前写出的资料库）
- **THEN** 该记录仍被正常读取并按既有语义恢复：歌曲 UUID、路径、内容哈希与元数据保持，入库时刻不伪造为虚假时间；“最近添加”顺序与该版本既有兜底行为一致，不产生错误、不丢弃歌曲

### Requirement: 新设备资料库重建

当用户在设置中选择同一资料库并连接其同步资料后，或者当用户重新打开一个已经具备可携带控制面的资料库目录时（包括卸载重装、清除本机应用数据目录，或把资料库目录从另一台机器拷入），系统 MUST 先验证 manifest 的资料库逻辑 ID 和格式兼容性，再将对象资料投影到本机数据库，并扫描 `media/` 关联文件。歌曲、收藏、歌单、歌单成员、覆盖层和播放统计 MUST 按原 UUID 恢复；对象资料存在但对应媒体尚未就绪时，系统 MUST 保留该对象并将歌曲标记为不可用，而不得分配替代 UUID 或丢弃歌单成员。重建 MUST 幂等：对同一目录重复执行不产生第二份对象，也不改变既有 UUID。

#### Scenario: 全新设备恢复完整资料
- **WHEN** 新设备取得一个含有媒体和完整可携带对象资料的资料库
- **THEN** 设置完成后，该设备重建与原设备一致的歌曲 UUID、我的喜欢、歌单、歌单成员顺序与播放统计，并可通过相对路径播放已校验媒体

#### Scenario: 同步资料先于媒体到达
- **WHEN** 新设备已获得歌曲、收藏和歌单对象资料，但 `media/` 中尚未存在某首歌曲
- **THEN** 系统显示该歌曲为不可用并保留所有 UUID 关联；媒体随后到达且哈希校验成功时恢复可用，不产生第二首歌曲

#### Scenario: 本机数据库丢失后重开同一资料库
- **WHEN** 本机应用数据目录被清除或应用被重装后，用户重新选择此前使用过的同一资料库目录
- **THEN** 系统按该目录的 `echo/` 对象资料恢复歌单、歌单成员顺序、「我的喜欢」与播放统计，歌曲 UUID 与该目录对象资料一致，且重新扫描 `media/` 不会产生新的 UUID

#### Scenario: 重复打开结果稳定
- **WHEN** 用户对同一资料库目录连续两次执行打开与重建
- **THEN** 对象数量、UUID、歌单成员顺序与播放统计与首次一致，不产生重复歌曲、重复歌单或重复成员

### Requirement: 控制面存在性与自愈

对一个被启用为受管资料库的可写目录，系统 MUST 保证 `echo/manifest.json` 存在，且其中记录资料库逻辑 ID 与格式版本。首次启用时 MUST 建立该 manifest；打开资料库发现 manifest 缺失但 `echo/records/` 已有对象资料时，系统 MUST 依据该目录既有对象资料自愈重建 manifest，并保留全部对象与 UUID，不得因此把该目录当作新资料库重新扫描并铸造新标识。当 `echo/` 无法安全创建或更新时，系统 MUST NOT 就地覆盖或删除既有控制面文件，MUST 明确报告控制面不可用，且 MUST NOT 静默把本机数据库当作唯一存储继续接受逻辑变更。

#### Scenario: 首次启用即建立 manifest
- **WHEN** 用户首次把一个可写目录启用为受管资料库并导入第一首歌
- **THEN** 该目录出现 `echo/manifest.json`，包含稳定的资料库逻辑 ID 与格式版本，后续写入的对象资料与该 manifest 位于同一 `echo/` 下

#### Scenario: manifest 缺失时自愈
- **WHEN** 一个已有 `echo/records/` 对象资料但没有 `echo/manifest.json` 的目录被重新打开
- **THEN** 系统建立与该目录既有对象资料一致的 manifest，保留全部对象资料与 UUID，并在本次打开中报告一次自愈；不因 manifest 缺失而重新铸造歌曲标识

#### Scenario: 控制面不可写时不破坏既有内容
- **WHEN** 资料库目录可读但 `echo/` 无法安全创建或更新
- **THEN** 系统保留既有控制面文件原样不动，把该资料库置于只读语义并明确报告控制面不可用，不把逻辑变更写进无法材料化它们的本机数据库

### Requirement: 对象资料接续与对账

在把资料库目录设为活动根目录并扫描 `media/` 之前，系统 MUST 先读取该目录的对象资料，并按其中的 UUID 接续本机状态；对已经拥有对象资料的歌曲，系统 MUST NOT 因为本机缺少记录而在扫描中重新铸造 UUID。对象资料与 `media/` 不一致时，系统 MUST 保留对象并把对应歌曲标记为不可用，而不是丢弃其收藏、歌单成员或播放统计关联。同一 `media/` 文件在本机已经有一行、而该行的 UUID 与对象资料不同时，系统 MUST 以本机行为准（较新的事实），MUST NOT 为同一文件再建第二行，也 MUST NOT 改写既有 UUID。接续、对账与投影 MUST 幂等；被墓碑取代的对象 MUST NOT 在当前有效视图中复活。

#### Scenario: 打开资料库先接续再扫描
- **WHEN** 用户打开一个 `echo/` 中含对象资料、而本机数据库尚无对应记录的资料库目录
- **THEN** 系统先按对象资料把歌曲、收藏、歌单、成员与播放统计投影到本机数据库，再扫描 `media/` 关联媒体，已由对象资料拥有的媒体在本次扫描中不会被当作新文件铸造新 UUID

#### Scenario: 对象资料与媒体不一致
- **WHEN** 对象资料描述了某首歌但 `media/` 中不存在其文件，或 `media/` 中存在没有对象资料的文件
- **THEN** 前者保留对象并显示为不可用，后者在控制面可用时被登记为新对象而不是每次打开都重复登记；两种情况都不改写既有 UUID

#### Scenario: 墓碑优先于陈旧记录
- **WHEN** 同一对象同时存在一份对象记录与一份版本更新的墓碑
- **THEN** 该对象不出现在当前有效视图（曲库、歌单、我的喜欢）中，也不会因为再次打开资料库而被复活

#### Scenario: 重复接续结果稳定
- **WHEN** 系统对同一资料库目录重复执行接续与对账
- **THEN** 对象数量、UUID、歌单成员顺序与播放统计与首次一致，且不产生重复对象记录

#### Scenario: 较新的本机身份不被旧记录覆盖
- **WHEN** 对象资料里的一首歌与本机已有的一行指向同一个 `media/` 文件，但两者 UUID 不同（本机行是后续扫描重新铸出的较新身份）
- **THEN** 系统保留本机行的 UUID 与状态、不为该文件再建第二行、不改写既有 UUID，并在对账报告里把该记录计为被取代；记录文件本身保留在 `echo/` 中
