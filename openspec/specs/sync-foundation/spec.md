# sync-foundation Specification

## Purpose
让 Echo 本地数据的**存储形状**从 0.1.0 起就可被二期同步引擎消费，同时严格保持本期"离线、无账号、无网络、无可操作同步入口"的生产边界。本 capability 只建立同步基础数据的 schema、对象 revision 与本地 outbox 预写，不提供远端连接、转换、冲突裁决或 UI 入口。

## Requirements

### Requirement: 同步基础数据形状（schema 骨架）

系统 MUST 为同步引擎固定数据形状：全部可同步候选对象（歌曲、收藏、歌单、歌单成员、覆盖层、资料库根目录）携带单调递增的整体 `revision`、写入设备逻辑 ID 和可比较的混合逻辑时间；本地最终删除保存于 `tombstones`，可撤销删除独立保存本机意图；远程配置与同步游标保存于 `sync_state`；待上传的逻辑变更保存于 `sync_outbox`。可同步对象 MUST 能投影为资料库 `echo/records/` 中版本化对象资料，且暂存目录 `echo/tmp/` 不得进入同步载荷。上述表与字段 MUST 通过新增的顺序迁移落地，且不得改动已发布的 `0001` 迁移。根目录仅共享逻辑身份，不共享本机路径。

#### Scenario: 数据形状已就绪且离线边界不变
- **WHEN** 所需迁移执行后，数据库 schema 包含 `tombstones`、`sync_state`、`sync_outbox` 三张表及全部同步候选对象的版本和写入顺序字段
- **THEN** 同步默认关闭时系统不发现、不监听、不连接、不上传/下载；用户显式启用后允许消费这些事实，网络依赖只由适配器装配，WebView不直接访问网络，UI可提供同步配置与状态入口

#### Scenario: 对象级 revision 单调递增
- **WHEN** 一首歌、收藏、歌单、歌单成员、根目录或覆盖层发生任何本地逻辑变更（导入、收藏切换、歌单增删成员、覆盖层写入、删除）
- **THEN** 该对象的 `revision` 单调递增，写入顺序字段可确定同一对象两次变更的先后，且本地高并发顺序提交不产生倒退或跳号；本地 revision 与主确认版本独立，清理 outbox 不得使其回退

### Requirement: 本地变更预写 outbox

系统 MUST 对全部本地逻辑变更（歌曲导入/编辑、收藏切换、歌单增删成员、覆盖层、最终删除）执行“预写 outbox”：把变更事件作为一条待上传记录写入 `sync_outbox`，并生成或更新相应的可携带对象资料，使本地数据从首日起即为可同步形状。本机可撤销删除 MUST 先保存独立 intent/journal，PendingDelete 与其临时墓碑不得成为可提交事件或共享最终墓碑；窗口内撤销取消意图，窗口结束后的逻辑终结与稳定删除事件 MUST 同事务提交。启用局域网同步时 MUST 从完整对象资料建立历史基线，为后续本地变更持久化稳定 mutation 身份、来源顺序与待确认状态；远端已确认结果应用 MUST NOT 再生成本地上传事件。播放统计等其余共享对象 MUST 同样具备可恢复变更捕获，不依赖文件写出与数据库事务天然原子。

#### Scenario: 导入与收藏变更是 outbox 条目
- **WHEN** 用户导入歌曲或将歌曲设为收藏，以及歌单增删成员、覆盖层写入或最终删除终结
- **THEN** 对应 `sync_outbox` 行被创建，携带对象类型、对象 UUID、递增 revision、写入顺序、操作类型和全量对象载荷；且本条变更同时已提交到对应正表并立即可被本地读取

#### Scenario: 预写不产生可操作同步
- **WHEN** 任何本地变更导致 `sync_outbox` 行增长
- **THEN** 同步未启用时系统不初始化远程连接或尝试上传；outbox 作为本地持久化队列保留，启用后历史基线与新事件按同步协议消费，不将旧全快照当作新编辑重放

#### Scenario: 可撤销意图不成为同步墓碑
- **WHEN** 历史库升级/启用同步时存在 PendingDelete 和临时 portable 墓碑，或用户在窗口内撤销删除
- **THEN** 先按可验证的 operation journal 恢复本机意图，未终结意图不进入最终墓碑/可提交 outbox/历史删除基线；撤销保留原 UUID 和关联，终结仅产生一次稳定删除事件；缺少足以区分临时墓碑与最终删除的 journal 时，迁移必须保留原始文件并拒绝启用同步，不得猜测或丢弃

### Requirement: 墓碑

系统 MUST 持久化逻辑删除的墓碑，使删除这一操作本身就是可同步的本地事实（而非仅删除歌曲记录）。墓碑行 MUST 记录删除对象的类型、UUID、revision 与删除时间。

#### Scenario: 删除产生墓碑
- **WHEN** Echo 主动删除歌曲或歌单（非外部文件缺失）
- **THEN** 系统写入一条 `tombstones` 行，记录对象类型、UUID、revision 与删除时间；对象正表行保持或按删除语义收敛，二期可据此进行跨端传播删除

### Requirement: 可同步载荷不含本机路径

系统 MUST 沿袭 `local-library`「绝不把根目录绝对路径写入歌曲关联或用户可同步数据」的约束：当同步基础数据（`sync_outbox` 全量载荷、`tombstones`、对象 revision）成为可同步数据的载体时，其载荷只包含对象 UUID、相对路径与对象字段，绝不包含本机绝对路径、数据库文件路径、凭据或网络端点。

#### Scenario: 本机绝对路径不进入可同步载荷
- **WHEN** 任何同步基础数据（`sync_outbox` 载荷、`tombstones`、对象 revision）被序列化或导出
- **THEN** 载荷中不出现根目录绝对路径、数据库文件路径、账号/凭据或网络端点，只包含逻辑 ID、相对路径与对象字段

### Requirement: 同步事件可重试且按类型识别

系统 MUST 以资料库、来源设备和稳定 mutation 身份识别重试事件，以对象类型与 UUID 识别对象、墓碑及歌曲/成员别名；主设备确认结果 MUST 可重复返回，远端应用、对象游标及日志摘要 MUST 一致持久化。成员去重映射 MUST 可从日志/快照/控制面恢复，不得修改已发送事件正文，已删除成员的旧别名不得重新指向新成员。升级 MUST 使用新顺序迁移并保留原 UUID、revision 高水位与全部历史可携带事实。上述规则 MUST 位于共享核心，传输通过端口接入，遵守工程规范 §3–§5、§8–§9；不得使用会重新预写 outbox 的本地更新操作直接替代远端应用。

#### Scenario: 网络重复提交
- **WHEN** 客户端重复提交同一 mutation，且上次确认响应未送达
- **THEN** 主返回相同持久化结果，不新增业务效果；相同 mutation 身份但内容不同被拒绝

#### Scenario: 远端应用及游标恢复
- **WHEN** 从设备应用主确认结果后崩溃并重启
- **THEN** 该结果与已应用水位一致恢复，不重复生成本地上传事件，不跳过尚未应用的事实

#### Scenario: 迁移与架构验证
- **WHEN** 同步基础升级准备交付
- **THEN** 新旧库迁移及重复升级、对象类型墓碑隔离、revision 不回退和事件去重契约测试通过，cargo fmt/clippy/test及架构门禁证明向内依赖、事务与网络隔离

### Requirement: 本地候选与确认事实独立于 SQLite

所有已提交本地业务变更 MUST 在同一音乐库提交内保存足以恢复其候选的对象身份、完整载荷、基线、稳定 mutation 身份、冻结时间、来源顺序和前驱；SQLite outbox 是此事实的投影。远端确认及拒绝对候选的终结 MUST 同样可从目录恢复。真实已确认完整载荷 MUST 与更新的本地候选分开保存，不得因复制旧版本收据而把新值冒充为已确认。恢复必须保留已发送正文、revision 高水位、typed alias/墓碑及逐设备统计的幂等性。

#### Scenario: 重建 outbox
- **WHEN** 已保存本地编辑尚未上传，SQLite 随后丢失而资料库保持完整
- **THEN** 系统恢复相同用户意图及原候选身份/前驱，不把旧快照重新当作新编辑，不退回 revision，也不以新的等价事件重复加统计或成员

#### Scenario: 远端确认后重建
- **WHEN** 远端结果及其目录确认资料已经持久化，之后本机数据库丢失
- **THEN** 重建能区分已终结事件和仍待确认候选，不把已确认事件重新上传；无可信会话证据时保留资料且停止旧绑定续传

#### Scenario: v2 本地覆盖值混有旧确认元数据
- **WHEN** 升级读取的记录包含本地更新值和旧 sync metadata，但无证据证明该载荷已确认
- **THEN** 系统保留原件并将其标记为待核对或待确认，不以旧 object version 为该新值建立虚假的 confirmed baseline

### Requirement: 新绑定显式接纳旧待确认意图

可信原会话恢复 MUST 使用原 mutation 与前驱链；重新配对导致 binding、epoch 或作者变化时，旧已发送事件 MUST 保持只读证据且不得直接授权重发。系统 MUST 先核对主规范状态、alias/墓碑和可验证旧 receipt，再为仍需提交的意图持久保存一次旧事件到新事件的接纳映射，创建新绑定/作者下可授权事件。转换 MUST 保留对象 UUID、原冻结时间、成员顺序及统计设备桶，使用对账后真实基线；无法判断是否已接纳的意图必须保留待处理，不能盲重放。普通 SQLite 重建不触发此转换。

统计桶的保留 MUST NOT 使新作者提高旧作者的未确认桶或将其差额改记为新作者播放；只有原作者授权可验证恢复时才可继续该桶的提交，否则完整保留本地计数及旧候选并标记待处理，遵守既有逐作者授权规则。

#### Scenario: 新身份接纳过程被中断
- **WHEN** 用户重装后重新配对并接纳仍未确认意图，在新事件创建或响应前退出
- **THEN** 重启依持久映射继续同一转换，仅产生一个新事件，旧已发送正文不改写，已被主接纳或最终删除的意图不重复应用

#### Scenario: 无法证明旧事件是否已确认
- **WHEN** 新会话对账不能确定某旧事件是否已被接纳
- **THEN** 系统保留用户意图和资源供显式处理，不静默丢弃，也不把整个当前快照作为新编辑自动上传

#### Scenario: 新作者不能抬高旧作者统计桶
- **WHEN** 原作者 A 本地桶为 7、主已确认 A 桶为 5，重装后新作者 B 无法证明原作者授权
- **THEN** 本地完整保留 A=7 及旧待确认事件并说明需处理，不由 B 上传 A=7 或把差额 2 移入 B 桶；B 的后续真实播放独立记入 B 桶，不重复加计

### Requirement: 远端应用和派生变更不制造上传回声

远端增量、快照、ACK、别名规范化、资料库重建和数据库投影重放 MUST 按来源区分，不生成等价本地 mutation。只有真实本地业务变化进入候选；无变化扫描、本机文件可用性及投影检查点不构成共享编辑。Application 通过端口协调目录提交与 SQLite 投影，遵守工程规范 §3–§5、§8–§9 及 `library-durability` LD-10。

#### Scenario: 反复恢复与 watcher
- **WHEN** 已接收对象被目录重放、SQLite 重建，随后 watcher 观察到同步发布文件
- **THEN** 对象、关系及候选数量稳定，无等价回传事件，恢复后空闲同步仍可收敛
