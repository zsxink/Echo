# library-durability Specification

## Purpose

确保本地音乐库独立保存可恢复的用户资料，使歌曲、喜欢、歌单及其资源在应用重装、SQLite 损坏和操作中断后仍能恢复，并对历史缺口、尚未保存及尚待更新视图的状态给出真实且可验证的反馈。

## Requirements

### Requirement: LD-01 本地音乐库权威提交

系统 MUST 将音乐库目录中的已提交资料定义为用户数据的唯一持久事实来源，SQLite 仅作为可重建投影。所有来源的歌曲、喜欢、歌单、成员、覆盖层、逐设备统计、类型化墓碑、必要别名与用户资源变更 MUST 先可靠提交到本地音乐库，再提交其业务数据库投影。交互式本地编辑在目录提交确认后 MUST 可立即返回已保存状态；**除收藏这类用户单次点击即可感知的写入外**，SQLite 投影可在后台滞后，SQLite 写锁或投影失败不得阻塞已保存确认。系统 MUST 区分未保存、已保存但待投影和已完成；SQLite 提交成功不能替代音乐库保存成功。格式、权限、空间或刷盘失败 MUST 可见，且不得继续接受仅写数据库的用户变更。

**收藏这类用户单次点击即可感知的写入 MUST 在返回已保存前完成其 SQLite 读模型投影**，使返回后立即读取的歌曲列表、喜欢视图与收藏计数已经是该次写入的权威结果，不得仍呈现写入前的旧值。此类写入的投影失败 MUST 仍按「已保存待投影」报告并保留稳定操作身份：目录提交已经发生，系统 MUST NOT 把它误报为未保存，MUST NOT 静默丢弃，也 MUST NOT 为同一意图创建第二个对象。

同步投影 MUST 只覆盖本次写入对应的增量提交（自当前投影水位起按目录链顺序幂等追赶），MUST NOT 因一次收藏而重放整库历史。

#### Scenario: 本地写入失败
- **WHEN** 音乐库控制面不可写或持久化失败，而 SQLite 仍可写
- **THEN** 用户变更不以普通成功返回，SQLite 不产生独占的新业务事实，原已提交资料保留，用户获得可重试或需处理的原因

#### Scenario: 目录已提交而投影失败
- **WHEN** 本地音乐库已提交完整变更，SQLite 投影随后失败
- **THEN** 系统明确返回已保存待投影及稳定操作身份，保留变更并可重试/重建视图，不能把该变更误报为未保存或创建第二个对象

#### Scenario: SQLite 投影滞后时连续本地编辑
- **WHEN** 第一条歌单编辑、导入或其它非收藏的本地编辑已可靠提交到目录而 SQLite 仍落后，用户立即发起第二条操作
- **THEN** 第二条操作从有序权威状态读取第一条已保存事实并分配正确版本；前台不等待 SQLite 追平，投影 worker 按目录序号提交完整业务行与同一事务内的连续水位，重启后可从该水位重放

#### Scenario: 收藏写入返回后立即回读已是新值

- **WHEN** 用户对一首歌曲执行收藏，目录提交确认后系统返回已保存
- **THEN** 返回后立即读取该歌曲所在列表、喜欢视图与收藏计数，三者均已是收藏后的值，不得仍呈现收藏前的旧值

#### Scenario: 收藏的投影失败仍报告为已保存待投影

- **WHEN** 收藏的目录提交已成功，但随后的 SQLite 投影失败
- **THEN** 系统返回已保存待投影及稳定操作身份，收藏意图保留且可重试重建，不得误报为未保存，也不得为同一意图创建第二个收藏事实

#### Scenario: 收藏写入只追平增量投影

- **WHEN** 音乐库目录已有若干历史提交、SQLite 投影水位落后若干条，用户执行一次收藏
- **THEN** 该次写入只投影自当前水位起的增量提交，不重放整库历史，且收藏写入本身按收藏场景的同步投影规则完成

### Requirement: LD-02 多对象提交与中断恢复

系统 MUST 为一次逻辑操作的全部对象、关联和资源声明提供可验证的集合提交边界。恢复所需数据 MUST 位于音乐库目录并独立于 SQLite；多次文件替换或一个数据库事务不得被视为跨资源原子保证。已提交集合 MUST 可重复重放；未提交集合不得被扫描、恢复或同步导出为完整操作；进程在提交结果不确定时 MUST 先核对原操作身份。仍被提交集合、候选、快照、冲突或删除意图引用的唯一资源 MUST NOT 被清理。

已提交集合 MUST 有独立于 SQLite 和远端水位的可验证本库顺序与前驱，恢复及延迟投影必须保持该顺序；目录内的持久材料化检查点 MUST 足以证明哪些历史可安全压缩，不能用旧操作覆盖较新业务值。业务投影 MUST 从已记录的投影水位起按目录链顺序幂等追赶，不得只投影最近一次操作；单次操作成功不能使更早未投影的提交永久丢失。

#### Scenario: 级联删除写到一半崩溃
- **WHEN** 一次歌单删除或歌曲最终删除涉及多个对象，进程在部分记录材料化后退出
- **THEN** 重启先恢复该集合再开放读写，恢复结果为同一完整逻辑提交，不能出现半套成员或复活已删除对象

#### Scenario: 丢失 SQLite 后重放
- **WHEN** 目录提交完成后 SQLite 尚未更新就被移走，应用重新打开完整目录
- **THEN** 系统从目录恢复该提交，原 UUID、对象值及关系保持，重复重放不增计数、不新增成员、不生成回传事件

#### Scenario: 提交结果不确定
- **WHEN** 提交标记的持久化返回错误或完成响应丢失
- **THEN** 重试先查询同一稳定操作身份，不以新 UUID 或新事件盲重做，未确认状态不得显示普通保存成功

#### Scenario: 较旧操作延迟重放
- **WHEN** C1 已提交但投影失败，C2 随后成功改动同一对象，之后重启或压缩日志
- **THEN** 依据目录提交链和材料化检查点按序恢复，最终值保持 C2，C1 重试不回退它；缺失或断链必须报告而非依赖数据库猜顺序

#### Scenario: 本地提交后对象文件材料化失败
- **WHEN** 完整目录提交可靠后，部分对象文件的材料化失败，SQLite 尚未投影
- **THEN** 明确返回已保存待恢复及失败阶段，保留完整提交且暂停受影响读取/导出，重启先补齐目录，不能把该操作当作未保存重建新对象

### Requirement: LD-03 全新环境离线重建

用户仅保留完整音乐库目录、失去全部应用数据且断网时，系统 MUST 能恢复已提交的歌曲 UUID/路径/哈希/原入库时刻、喜欢 true/false、歌单定义、成员 UUID/追加顺序/已知加入时间、用户封面与覆盖层、逐设备播放桶、类型化墓碑及可证明别名。派生索引与缩略图 MUST 可重新生成。缺失媒体 MUST 仅影响可播放性，不能丢弃逻辑对象及关系。恢复 MUST 幂等且不得伪造历史缺失字段。

#### Scenario: 本地与同步来源混合恢复
- **WHEN** 用户在新安装的离线 Echo 中打开含有本地导入、扫描和 LAN 接收数据的完整资料库
- **THEN** 三种来源的已提交数据按同一身份和关系恢复，不依赖旧 SQLite、网络或来源设备，恢复后媒体可用状态符合真实文件校验结果

#### Scenario: 部分媒体缺失
- **WHEN** 歌曲与关系记录有效而音频尚未下载或已被外部移走
- **THEN** 歌曲与喜欢/成员仍保留原 UUID，标记不可用，文件到达并验证后关联原对象，不创建替代歌曲

### Requirement: LD-04 支持格式的只读兼容

系统 MUST 按支持的旧格式读取可识别对象和历史缺省字段，保留原有身份及关系表示；兼容读取不得写回或改造旧记录、补造时间、从 SQLite 救援资料、回填缺失对象或自动修复身份与关系。无法解释的数据应保留原件并明确报告，不得宣称已完成历史修复。

#### Scenario: 读取旧格式记录
- **WHEN** 用户打开含有支持版本旧格式记录的音乐库
- **THEN** 系统按该格式读取已表达的资料及关系，不改变记录身份或内容，不补造缺失字段，也不从旧 SQLite 回填资料

#### Scenario: 旧记录含无法解释的关系
- **WHEN** 支持格式中的关系引用无法解析
- **THEN** 系统保留原始记录并报告未解析状态，不臆造父对象、不重写身份或关系，也不将其描述为已修复

### Requirement: LD-05 运行期间不得自动改写身份

系统 MUST 保持已提交对象身份及其关系原文。SQLite 新生成的身份、相同路径或相似标签均不得触发自动合并、引用重写或历史身份修复；证据不足或冲突时 MUST 保留双方资料并报告，不得改写已发送事件或复活已终结身份。本地映射 MUST NOT 冒充主确认 alias。此要求不构成修复既有旧库身份的义务。

#### Scenario: 运行期间发现身份冲突
- **WHEN** 已提交对象与新扫描或投影身份不同，且现有协议事实不能证明二者为同一身份
- **THEN** 系统保留各自身份和引用并报告冲突，不因路径、墙钟或音乐键自动合并或改写关系

### Requirement: LD-06 不完整资料不得被静默破坏

系统 MUST 保留新协议运行期间遇到的损坏、未知格式及无法解析关系的原记录，并说明对象标识和原因。投影 MUST 容忍无法解析的父引用：可解析对象照常投影，无法解析关系保留原件并标记未解析，不得因单条悬空引用使整个重建失败，也不得臆造父对象或自动补全历史关系。音频不能推导历史喜欢、歌单名或顺序；此要求不承诺修复旧库。

#### Scenario: 新协议投影遇到悬空关系
- **WHEN** 新协议已提交资料含有无法解析的歌曲或歌单引用
- **THEN** 可解析对象仍可投影，关系原件保留并报告未解析，不使整个投影失败，也不生成推测的父对象

#### Scenario: 控制面含损坏记录
- **WHEN** 一个新协议对象无法解析或摘要不符，其他对象仍有效
- **THEN** 已验证的独立资料可只读浏览，损坏原件保留并说明原因，不自动删文件或把损坏当作空库

### Requirement: LD-07 已确认基线与待确认资料分别恢复

音乐库 MUST 保存可证明的已确认完整载荷及其版本/typed alias，并独立保留本地未确认候选的稳定身份、基线、前驱和已发送正文。系统 MUST NOT 将附有旧确认元数据的新本地业务值认定为已确认载荷。SQLite 重建 MUST 保留当前有效用户值、未确认意图与冲突资料；恢复和远端应用不得产生等价的新上传事件。缺少可信会话/账本时 MUST 禁止旧会话续传，同时仍提供离线用户数据。

显式重新配对/恢复到新绑定或作者时，系统 MUST 先对账已接纳结果与旧事件，再通过一次持久可重试的意图接纳转换创建新授权事件，保留旧正文与映射证据，不直接改写或盲重发旧 mutation。无法证明是否已接纳的意图 MUST 保留待处理，不能自动作为新编辑上传。

#### Scenario: 离线改歌单后重装
- **WHEN** 设备已确认歌单名为 A，离线改为 B 后失去 SQLite，仅保留完整音乐库
- **THEN** 恢复视图保留 B，真实基线仍是 A，候选与已发送信息不伪装成已确认；无凭据时不自动联网，并提供重新配对/对账路径

#### Scenario: 主机账本不可验证
- **WHEN** 用户资料可恢复但旧主机安全检查点或确认历史不可验证
- **THEN** 系统不沿旧 epoch 提供服务，要求按既有显式恢复流程建立新 epoch；歌曲、喜欢、歌单和待确认意图仍可离线恢复

#### Scenario: ACK 丢失后重装并重新配对
- **WHEN** 旧事件可能已被主接纳但 ACK 丢失，用户重装后以新设备身份重新配对
- **THEN** 系统先核对主状态与可验证 receipt，已接纳意图不重复应用；尚需提交的意图经持久映射生成新授权事件，转换中断重试仅生成一次，旧正文不变、对象 UUID 与原冻结时间/统计桶保持，无法判定者保留待处理

### Requirement: LD-08 资源原件与实际位置可恢复

用户自定义封面、歌词及覆盖资源 MUST 以可校验原件及对象引用保存到资料库，不能仅依赖应用缓存 key。同步不可变媒体版本的实际库内位置及其 owner/version、长度和哈希 MUST 可从目录恢复；任意控制面文件不得成为媒体扫描入口。完整备份 MUST 保留仍被引用的受管版本资源。未校验文件不得标记可播放。

#### Scenario: 歌单封面脱离应用缓存恢复
- **WHEN** 用户设置歌单封面并保存，随后应用缓存和 SQLite 被全部移走
- **THEN** 系统从资料库内原件恢复同一歌单封面并重新生成缩略图，不显示只有失效 cache key 的已恢复结果

#### Scenario: 同步媒体使用不可变版本路径
- **WHEN** 已同步歌曲的实际文件在受管理的 `echo/media/` 版本路径中，用户重装应用
- **THEN** 系统按持久声明和哈希校验关联原歌曲 UUID，不依赖只扫描 `media/`，也不把 `echo/` 中任意文件作为歌曲导入

### Requirement: LD-09 格式读取兼容与一致备份边界

系统 MUST 对明确支持的旧格式提供兼容读取，不要求将既有旧库升级为新目录提交协议，也不得借格式读取执行历史资料救援、回填、身份或关系修复。不支持新目录提交协议的旧客户端 MUST NOT 写入已使用新协议的目录。未来未知格式 MUST 保持只读且不覆盖。只有媒体与控制面及所需恢复资料均完整的目录才承诺完整备份；仅保存音频或并发拷贝半套目录不得显示为完整备份。

#### Scenario: 支持的旧格式保持只读兼容
- **WHEN** 用户打开使用受支持旧格式的资料库
- **THEN** 系统可按旧格式读取既有资料，但不迁移或改写历史数据；对新协议专属写入明确拒绝或要求使用新建的受支持资料库

#### Scenario: 旧程序打开新协议目录
- **WHEN** 不支持新目录提交协议的旧程序尝试写入该目录
- **THEN** 格式检查拒绝写入，不忽略未完成提交或覆盖新对象

#### Scenario: 只保留 media
- **WHEN** 用户只有音频文件而没有用户对象及其关系记录
- **THEN** 系统可扫描恢复音频，但明确喜欢/歌单无法据此还原，不能宣称恢复全部数据

### Requirement: LD-10 分层与交付契约

持久化、迁移及恢复规则 MUST 位于共享 Core，用例通过端口协调目录事实与数据库投影；UI、播放器和传输适配器不得直接绕过此边界写用户数据。生产实现 MUST 遵守工程规范 §2–§6、§8–§9，包括向内依赖、小接口、顺序迁移、类型化错误、后台生命周期与跨平台路径。本 change 的自动化交付证据 MUST 覆盖受影响 crate、前端相关检查和小规模代表场景；完整 workspace 与三平台原生证据属于整体发布或后续独立验收，不能把未执行的规划、fixture 或单元测试描述成已验证结果。

#### Scenario: 可执行验证
- **WHEN** 本 change 按已完成范围准备验收
- **THEN** `cargo fmt --all --check`、受影响 crate 的 Clippy/测试、前端相关检查、IPC/架构、`pnpm verify:governance`、小规模代表场景及 `openspec validate --all --strict` 通过，并明确记录未执行的完整 workspace 或三平台原生验收，不将其作为本 change 短 CI 的门槛

### Requirement: LD-11 音乐库恢复状态排除单机同步状态

音乐库恢复状态 MUST 仅反映歌曲、用户资料、资源及其真实持久化/投影问题。没有有效同步上下文时，同步协议队列、候选和恢复记录 MUST NOT 被计入音乐资料待恢复数量或展示为音乐库恢复问题；系统 MUST 在启动恢复阶段清理可安全删除的旧同步投影状态，同时不得删除歌曲、喜欢、歌单、成员或媒体。

#### Scenario: 单机启动存在旧同步投影
- **WHEN** 单机资料库的 SQLite 中仍有旧版本遗留的同步队列或同步恢复记录
- **THEN** 启动恢复清理这些同步专用投影，用户看到的音乐库恢复状态不包含它们，真实音乐资料和媒体保持可用

### Requirement: LD-12 自定义封面原件写入前必须确认内容真实性

系统 MUST 在把用户选择的封面字节提交为资料库内可校验原件之前确认：字节的实际图片容器格式与调用方声明的 MIME 一致，且该容器的头部可被解码器解析出有效尺寸。声明与实际内容不一致、无法识别为图片、或容器头损坏/截断的字节 MUST 在**保存阶段**以可识别的校验错误拒绝；MUST NOT 写入目录原文件、写入封面缓存、替换已保存封面、提交引用该资源的对象记录，也不得覆盖用户已输入的其它编辑内容。

声明类型 MUST 仍是 `image/jpeg`、`image/png`、`image/webp` 三者之一，且 MUST 与实际探测结果一一对应；体积非空且不超过 5 MiB、MIME 白名单、内容寻址、封面缓存磁盘布局、`cover://` 档位与缩略图生成语义 MUST 保持不变。校验 MUST NOT 因整幅像素解码而在保存路径引入与图像尺寸成正比的内存分配，也 MUST NOT 因解码器默认尺寸上限而拒绝原本可保存的合法封面；校验边界是容器头可解析，不得被表述为「整幅图像已验证可解码」。

该校验 MUST 位于共享 Core 的封面写入边界；歌单封面、艺人封面以及从目录读取已保存原件的路径 MUST 共用同一校验，UI 与平台壳 MUST NOT 拥有第二套写入规则。从目录读取时，已存在的无效原件 MUST 以明确的校验错误报告，MUST NOT 作为可展示封面写入缓存；不迁移、不删除、不回填该原件或其对象记录（与 `LD-06` 一致）。仅有历史缓存 key 而没有目录原件的封面 MUST 沿用既有恢复语义，不受本校验约束。

生产实现 MUST 遵守 CODE_STANDARDS §2、§3.1–§3.2、§4.1–§4.2、§8、§9：属于 Core Application 的输入校验，依赖方向仍为 Platform → Application → Domain（Infrastructure 通过既有 Port 接入），不新增跨层依赖、公开接口或外部依赖；错误继续使用既有可匹配的类型化校验错误。实现前 MUST 以当前 HEAD 复核 `artwork.rs` 的调用点与 `image` 特性；可执行验收证据 MUST 包含 `cargo test -p echo-core --all-features artwork::tests`、`cargo test -p echo-core --all-features --test arch`、`cargo test -p echo-desktop --all-features playlist_cover`、`cargo fmt --all -- --check`、`cargo clippy -p echo-core --all-targets --all-features -- -D warnings`、`pnpm verify:governance` 与 `openspec validate --all --strict`。本 change 不替换既有实现、导出、测试替身或登记资产，故无待清理残留；若实施中出现不再被解析的替代实现，MUST 按 §9 以引用检查与静态检查证明清理完成。

#### Scenario: 伪图片在保存阶段被拒绝

- **WHEN** 用户为歌单或艺人选择一段文本、压缩包等任意非图片字节并声明 `image/png` 后保存
- **THEN** 系统返回可识别的校验错误并说明原因，不写目录原件与封面缓存，不替换已保存封面与其它编辑内容，也不提交新的资源引用

#### Scenario: 声明类型与实际格式不一致被拒绝

- **WHEN** 提交声明为 `image/png` 但实际是 JPEG、WebP、GIF 或其它容器的字节，或声明为 `image/jpeg` / `image/webp` 而实际是另一种白名单格式
- **THEN** 系统在保存阶段拒绝并说明「声明类型与实际内容不一致」，不写入任何封面资源

#### Scenario: 容器头损坏被拒绝

- **WHEN** 提交仅带合法 JPEG/PNG/WebP 签名、但容器头截断、结构非法或无法解析出有效尺寸的字节
- **THEN** 系统在保存阶段以校验错误拒绝，不把失败推迟到 `cover://` 展示阶段，也不写目录原件与缓存

#### Scenario: 三种合法格式均可保存并展示

- **WHEN** 用户分别提交声明一致且容器头可解析出有效尺寸的 JPEG、PNG、WebP 封面
- **THEN** 三者都保存成功，目录原件的字节、长度、哈希与 MIME 与提交内容一致，并可经既有 `cover://` 路径读取

#### Scenario: 歌单与艺人封面共用同一校验

- **WHEN** 同样的伪造封面字节分别经歌单封面与艺人封面写入路径提交
- **THEN** 两条路径都在写入目录原件之前以同一类校验错误拒绝，不存在只校验其中一条的绕行入口

#### Scenario: 校验只读取容器头

- **WHEN** 提交声明一致、容器头可解析出有效尺寸、但不含完整像素数据的超大尺寸容器（例如仅含合法 IHDR 的 20000×20000 PNG 头）
- **THEN** 校验按「容器头可解析」的既定边界通过，不分配与像素数成正比的内存，也不因解码器默认尺寸上限驳回；该路径 MUST NOT 被声称已验证整幅图像可解码

#### Scenario: 既有体积与白名单语义不变

- **WHEN** 提交空字节、超过 5 MiB 的字节，或声明 `image/gif` 等白名单外的 MIME
- **THEN** 系统仍按既有体积/白名单规则拒绝，拒绝原因不被新的内容校验掩盖，且不产生 panic、静默成功或新的资源写入

#### Scenario: 既有无效原件与历史缓存-only 封面的兼容

- **WHEN** 资料库中已有指向非图片字节的目录原件，或仅有历史 cache key 而无目录原件的封面记录被读取
- **THEN** 前一种情况返回明确的校验错误，不写入缓存、不删除或改写原件与对象记录；后一种情况沿用既有 cache-only 恢复语义，不因新校验失效
