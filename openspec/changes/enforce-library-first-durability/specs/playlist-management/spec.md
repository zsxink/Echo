# playlist-management Delta

## ADDED Requirements

### Requirement: 歌单与成员以音乐库持久结果反馈

歌单创建、重命名、删除、封面修改及成员添加/移除 MUST 在音乐库可靠提交定义、关联、资源或类型化墓碑之后才投影 SQLite；普通成功反馈 MUST 发生于两者完成之后。目录已保存而投影失败 MUST 返回稳定操作身份及已保存待更新状态，不得当成可直接重新创建的未保存失败。未提交失败维持原界面；已提交待投影保留真实保存状态。批量操作 MUST 沿现有单项粒度报告，成员去重、追加顺序、时间及删除不影响音乐文件的语义保持。

#### Scenario: 创建空歌单后重装
- **WHEN** 用户成功创建没有任何成员的歌单，随后清除应用数据并重新选择原音乐库
- **THEN** 原歌单 UUID、名称和已知创建时间被恢复，不依赖成员记录推断其存在

#### Scenario: 多成员提交被中断
- **WHEN** 成员操作涉及多个记录，进程在目录已提交但数据库尚未投影时崩溃
- **THEN** 重启按原成员 UUID 和追加顺序恢复已提交项，重复请求不产生第二成员或重写原加入时间

#### Scenario: 保存与显示更新分离
- **WHEN** 重命名已提交到音乐库而 SQLite 暂时失败
- **THEN** 界面明确说明新名称已保存且等待更新，提供同操作重试，不将用户输入清空并诱导创建另一个歌单

#### Scenario: 删除与取消喜欢不复活
- **WHEN** 用户成功删除歌单/成员或取消喜欢，之后数据库被重建
- **THEN** 对应删除或 false 状态从音乐库恢复，旧记录不能使其重新出现，其他歌单和歌曲保持原有语义
