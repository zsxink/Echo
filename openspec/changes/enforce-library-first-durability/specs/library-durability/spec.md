# library-durability Delta

## Purpose

确保本地音乐库独立保存可恢复的用户资料，使歌曲、喜欢、歌单及其资源在应用重装、SQLite 损坏和操作中断后仍能恢复，并对历史缺口、尚未保存及尚待更新视图的状态给出真实且可验证的反馈。

## ADDED Requirements

### Requirement: LD-01 本地音乐库权威提交

系统 MUST 将音乐库目录中的已提交资料定义为用户数据的唯一持久事实来源，SQLite 仅作为可重建投影。所有来源的歌曲、喜欢、歌单、成员、覆盖层、逐设备统计、类型化墓碑、必要别名与用户资源变更 MUST 先可靠提交到本地音乐库，再提交其业务数据库投影。系统 MUST 区分未保存、已保存但待投影和已完成；SQLite 提交成功不能替代音乐库保存成功。格式、权限、空间或刷盘失败 MUST 可见，且不得继续接受仅写数据库的用户变更。

#### Scenario: 本地写入失败
- **WHEN** 音乐库控制面不可写或持久化失败，而 SQLite 仍可写
- **THEN** 用户变更不以普通成功返回，SQLite 不产生独占的新业务事实，原已提交资料保留，用户获得可重试或需处理的原因

#### Scenario: 目录已提交而投影失败
- **WHEN** 本地音乐库已提交完整变更，SQLite 投影随后失败
- **THEN** 系统明确返回已保存待投影及稳定操作身份，保留变更并可重试/重建视图，不能把该变更误报为未保存或创建第二个对象

### Requirement: LD-02 多对象提交与中断恢复

系统 MUST 为一次逻辑操作的全部对象、关联和资源声明提供可验证的集合提交边界。恢复所需数据 MUST 位于音乐库目录并独立于 SQLite；多次文件替换或一个数据库事务不得被视为跨资源原子保证。已提交集合 MUST 可重复重放；未提交集合不得被扫描、恢复或同步导出为完整操作；进程在提交结果不确定时 MUST 先核对原操作身份。仍被提交集合、候选、快照、冲突或删除意图引用的唯一资源 MUST NOT 被清理。

已提交集合 MUST 有独立于 SQLite 和远端水位的可验证本库顺序与前驱，恢复及延迟投影必须保持该顺序；目录内的持久材料化检查点 MUST 足以证明哪些历史可安全压缩，不能用旧操作覆盖较新业务值。业务投影 MUST 从已记录的投影水位起按目录链顺序幂等追赶，不得只投影最近一次操作；单次操作成功不能使更早未投影的提交永久丢失。

#### Scenario: 级联删除写到一半崩溃
- **WHEN** 一次歌单删除或歌曲最终删除涉及多个对象，进程在部分记录材料化后退出
- **THEN** 重启先恢复该集合再开放读写，恢复结果为同一完整逻辑提交，不能出现半套成员或复活已删除对象

#### Scenario: 丢失 SQLite 后重放
- **WHEN** 目录提交完成后 SQLite 尚未更新就被移走，应用重新打开完整目录
- **THEN** 系统从目录恢复该提交，原 UUID、对象值及关系保持，重复重放不增计数、不新增成员、不生成回传事件

#### Scenario: 提交结果不确定
- **WHEN** 提交标记的持久化返回错误或完成响应丢失
- **THEN** 重试先查询同一稳定操作身份，不以新 UUID 或新事件盲重做，未确认状态不得显示普通保存成功

#### Scenario: 较旧操作延迟重放
- **WHEN** C1 已提交但投影失败，C2 随后成功改动同一对象，之后重启或压缩日志
- **THEN** 依据目录提交链和材料化检查点按序恢复，最终值保持 C2，C1 重试不回退它；缺失或断链必须报告而非依赖数据库猜顺序

#### Scenario: 本地提交后对象文件材料化失败
- **WHEN** 完整目录提交可靠后，部分对象文件的材料化失败，SQLite 尚未投影
- **THEN** 明确返回已保存待恢复及失败阶段，保留完整提交且暂停受影响读取/导出，重启先补齐目录，不能把该操作当作未保存重建新对象

### Requirement: LD-03 全新环境离线重建

用户仅保留完整音乐库目录、失去全部应用数据且断网时，系统 MUST 能恢复已提交的歌曲 UUID/路径/哈希/原入库时刻、喜欢 true/false、歌单定义、成员 UUID/追加顺序/已知加入时间、用户封面与覆盖层、逐设备播放桶、类型化墓碑及可证明别名。派生索引与缩略图 MUST 可重新生成。缺失媒体 MUST 仅影响可播放性，不能丢弃逻辑对象及关系。恢复 MUST 幂等且不得伪造历史缺失字段。

#### Scenario: 本地与同步来源混合恢复
- **WHEN** 用户在新安装的离线 Echo 中打开含有本地导入、扫描和 LAN 接收数据的完整资料库
- **THEN** 三种来源的已提交数据按同一身份和关系恢复，不依赖旧 SQLite、网络或来源设备，恢复后媒体可用状态符合真实文件校验结果

#### Scenario: 部分媒体缺失
- **WHEN** 歌曲与关系记录有效而音频尚未下载或已被外部移走
- **THEN** 歌曲与喜欢/成员仍保留原 UUID，标记不可用，文件到达并验证后关联原对象，不创建替代歌曲

### Requirement: LD-04 历史资料救援与回填

对尚未满足本地权威要求的既有资料库，系统 MUST 在接续/扫描改写现存状态前保存从一致 SQLite 快照导出的目标库逻辑救援资料和原始目录记录，并按对象种类清点和回填真实缺失资料。目录内救援资料不得含原数据库文件、其他库、绝对路径、端点或凭据；恢复不得依赖原数据库仍存在。回填 MUST 可中断、可重复、按库隔离、保留时间/UUID/成员顺序且不伪造主确认信息；媒体缺失不构成放弃真实用户关系的理由。完成标记 MUST 以空数据库重建的规范用户状态比对为依据。

#### Scenario: 旧库有对象只有数据库保存
- **WHEN** 旧 SQLite 包含完整歌曲、喜欢、空/非空歌单和成员，而目录缺少对应记录
- **THEN** 系统先保存救援证据，将这些对象及资源按原身份写入目录，重建验证一致后才报告回填完成，重复升级不产生新身份或事件

#### Scenario: 回填途中断电
- **WHEN** 回填进行到一部分对象后中断，随后数据库被移走
- **THEN** 系统可依据目录内救援快照和迁移记录继续相同回填，不以当前不完整记录集误判完整，也不丢弃原始证据

#### Scenario: 一个数据库登记多个库
- **WHEN** 旧数据库包含多个根目录的数据而本次只打开其中一个
- **THEN** 仅救援属于目标库且可验证归属的数据，不把其他库的喜欢、歌单、凭据或媒体混入当前目录

### Requirement: LD-05 身份对账必须有证据

系统 MUST 优先采用已提交的资料库身份和可验证的规范 alias/墓碑；SQLite 行创建得更晚、路径相同或标签相似均不得独立证明它更权威。历史身份自动修复 MUST 有同库、完整内容及唯一身份对应或可信历史 alias/确认事实的证据，并保持所有喜欢、成员、覆盖层、统计、墓碑及候选引用一致。证据不足或冲突时 MUST 保留双方并报告，不得自动合并、改写已发送事件或复活已终结身份。本地迁移映射 MUST NOT 冒充主确认 alias。

#### Scenario: 旧喜欢引用 portable 身份
- **WHEN** portable 歌曲 A 与 SQLite 歌曲 B 被证明为同一未终结对象，旧喜欢引用 A、部分成员引用 B
- **THEN** 系统按可证明规范身份统一有效引用并持久保存修复证据，清空 SQLite 后仍能恢复全部关系，不因 B 较晚建立而跳过 A 的喜欢

#### Scenario: 同路径不同内容
- **WHEN** 两个 UUID 指向相同逻辑路径但哈希不同，且没有可信身份修复证据
- **THEN** 系统报告冲突并保留各自记录和可用资源，不按文件名、墙钟或音乐键自动丢弃其中一个

### Requirement: LD-06 不完整恢复必须可解释

系统 MUST 保留损坏、未知格式及无法关联的原记录，并给出按类型统计的恢复摘要与相对对象标识、原因和重试/处理入口。缺少父歌曲或歌单定义的关系不得被扫描后永久遗忘。投影 MUST 容忍无法解析的父引用：可解析的对象照常入投影，无法解析的关系保留原件并计入 partial 报告，不得因单条悬空引用使整个重建失败。只有全部应恢复对象及依赖验证通过才可标记整库完整；部分恢复 MUST 明确为 partial，阻止受影响对象的破坏性自动处理。音频不能推导历史喜欢、歌单名或顺序。

#### Scenario: 只有孤立喜欢与歌单成员
- **WHEN** 历史目录有 favorite/song_uuid 和 playlist-item，但所有可用证据均无父 Song 或歌单定义
- **THEN** 系统保留原记录并报告缺失依赖和可恢复范围，不编造歌曲对应、歌单名称或完整恢复成功

#### Scenario: 控制面含损坏记录
- **WHEN** 一个对象文件无法解析或摘要不符，其他对象仍有效
- **THEN** 已验证的独立资料可只读浏览，损坏原件保留，报告部分恢复及原因，不自动删文件或把损坏当作空库

### Requirement: LD-07 已确认基线与待确认资料分别恢复

音乐库 MUST 保存可证明的已确认完整载荷及其版本/typed alias，并独立保留本地未确认候选的稳定身份、基线、前驱和已发送正文。系统 MUST NOT 将附有旧确认元数据的新本地业务值认定为已确认载荷。SQLite 重建 MUST 保留当前有效用户值、未确认意图与冲突资料；恢复和远端应用不得产生等价的新上传事件。缺少可信会话/账本时 MUST 禁止旧会话续传，同时仍提供离线用户数据。

显式重新配对/恢复到新绑定或作者时，系统 MUST 先对账已接纳结果与旧事件，再通过一次持久可重试的意图接纳转换创建新授权事件，保留旧正文与映射证据，不直接改写或盲重发旧 mutation。无法证明是否已接纳的意图 MUST 保留待处理，不能自动作为新编辑上传。

#### Scenario: 离线改歌单后重装
- **WHEN** 设备已确认歌单名为 A，离线改为 B 后失去 SQLite，仅保留完整音乐库
- **THEN** 恢复视图保留 B，真实基线仍是 A，候选与已发送信息不伪装成已确认；无凭据时不自动联网，并提供重新配对/对账路径

#### Scenario: 主机账本不可验证
- **WHEN** 用户资料可恢复但旧主机安全检查点或确认历史不可验证
- **THEN** 系统不沿旧 epoch 提供服务，要求按既有显式恢复流程建立新 epoch；歌曲、喜欢、歌单和待确认意图仍可离线恢复

#### Scenario: ACK 丢失后重装并重新配对
- **WHEN** 旧事件可能已被主接纳但 ACK 丢失，用户重装后以新设备身份重新配对
- **THEN** 系统先核对主状态与可验证 receipt，已接纳意图不重复应用；尚需提交的意图经持久映射生成新授权事件，转换中断重试仅生成一次，旧正文不变、对象 UUID 与原冻结时间/统计桶保持，无法判定者保留待处理

### Requirement: LD-08 资源原件与实际位置可恢复

用户自定义封面、歌词及覆盖资源 MUST 以可校验原件及对象引用保存到资料库，不能仅依赖应用缓存 key。同步不可变媒体版本的实际库内位置及其 owner/version、长度和哈希 MUST 可从目录恢复；任意控制面文件不得成为媒体扫描入口。完整备份 MUST 保留仍被引用的受管版本资源。未校验文件不得标记可播放。

#### Scenario: 歌单封面脱离应用缓存恢复
- **WHEN** 用户设置歌单封面并保存，随后应用缓存和 SQLite 被全部移走
- **THEN** 系统从资料库内原件恢复同一歌单封面并重新生成缩略图，不显示只有失效 cache key 的已恢复结果

#### Scenario: 同步媒体使用不可变版本路径
- **WHEN** 已同步歌曲的实际文件在受管理的 `echo/media/` 版本路径中，用户重装应用
- **THEN** 系统按持久声明和哈希校验关联原歌曲 UUID，不依赖只扫描 `media/`，也不把 `echo/` 中任意文件作为歌曲导入

### Requirement: LD-09 新旧格式与一致备份边界

系统 MUST 可恢复升级历史 v1/v2 目录以支持新的目录提交协议，保留原始记录与迁移证据，并明确阻止不支持新协议的旧客户端写入。未来未知格式 MUST 保持只读且不覆盖。只有媒体与控制面及所需恢复资料均完整的目录才承诺完整恢复；仅保存音频或并发拷贝半套目录不得显示为完整备份。回滚 MUST 使用验证过的整套升级前备份或显式兼容导出。

#### Scenario: 旧程序打开升级目录
- **WHEN** 不支持新目录提交协议的旧程序尝试打开已升级音乐库
- **THEN** 格式检查拒绝写入，不忽略未完成提交或覆盖新对象；新程序可恢复未完成升级

#### Scenario: 只保留 media
- **WHEN** 用户只有音频文件而没有用户对象及其关系记录
- **THEN** 系统可扫描恢复音频，但明确喜欢/歌单无法据此还原，不能宣称恢复全部数据

### Requirement: LD-10 分层与交付契约

持久化、迁移及恢复规则 MUST 位于共享 Core，用例通过端口协调目录事实与数据库投影；UI、播放器和传输适配器不得直接绕过此边界写用户数据。生产实现 MUST 遵守工程规范 §2–§6、§8–§9，包括向内依赖、小接口、顺序迁移、类型化错误、后台生命周期与跨平台路径。交付 MUST 有自动化与原生证据，且不得把规划、fixture 或单元测试描述成真实资料库/三平台已验证。

#### Scenario: 可执行验证
- **WHEN** 本能力准备交付
- **THEN** `cargo fmt --all --check`、`cargo clippy --workspace --all-targets --all-features -- -D warnings`、`cargo test --workspace --all-features`、前端 format/lint/typecheck/test/build、IPC/架构及 `pnpm verify:governance`、`openspec validate --all --strict` 通过；LD-01 至 LD-09 的故障、重装与迁移矩阵及三平台原生文件操作证据可重复核对
