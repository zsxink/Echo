# Library durability acceptance evidence matrix

This matrix binds every scenario in `specs/library-durability/spec.md` (LD-01 through LD-10) to its specification anchor, current implementation evidence and the proof required for completion. Current code pointers identify known DB-first or partial recovery behavior; they do not satisfy the target. Automated tests, native tests and performance measurements remain pending until executed and recorded. See [`entrypoints.md`](entrypoints.md) for the wider import/scan/LAN entrypoint inventory and command catalogue.

## Evidence boundary

Evidence rows are based on the published `main` implementation (`2d07e7f`), never on this change's development branch; an in-progress branch must not be cited as proof of current behavior or of implemented capability.

The issue's 15-song / 2 portable song / 11 favorite / 3 member example is user-reported, not a fixture or a reproduced test. Fixtures for this change must use synthetic UUIDs, generated media bytes and temporary roots only. Recovery comparisons must compare normalized identities, paths/hashes/timestamps, favorite booleans, playlist definitions including empty playlists, member identities/order/times, resources, per-device buckets, tombstones/aliases and pending operations; aggregate row counts alone are insufficient.

Platform directory sync/rename semantics, permission and read-only behavior, crash recovery, long/Unicode paths, and performance at scale require recorded runs on native macOS, Windows and Linux hosts. No such results are asserted here. In particular, do not claim the full library is recoverable until the offline empty-DB reconstruction gate passes; legacy-format libraries are covered only by read-only compatibility, never by rescue or backfill.
