### 1. 歌单重试丢失稳定操作身份（已用 RED 复现固定，缺陷未修）

- 复现：`crates/echo-core/src/infrastructure/sqlite/tests/lifecycle/playlist_create.rs`
  `library_durability_playlist_create_retry_after_saved_pending_keeps_operation_identity`。
  该用例**已解除 `#[ignore]`**，当前观察到的行为 RED：

  ```
  panicked at crates/echo-core/src/infrastructure/sqlite/tests/lifecycle/playlist_create.rs:48:9:
  retrying a saved creation must report the same saved operation, got Storage { what: "sqlite",
    source: SqliteFailure(Error { code: ConstraintViolation, extended_code: 1811 },
    Some("injected create projection failure")) }
  ```

- 缺陷分两段，**第一段已被上述 RED 直接观测，第二段由代码路径确认、被第一段的失败遮住**：

  1. **追赶失败被原样返回**（已观测）。重试时协调器先做水位追赶
     （`local_library_edit.rs:235-249` 的 `project_commits`），追赶因注入的触发器失败。
     该处只在 `retry_operation` 命中 `StateKind::PlaybackEvent` 时才把错误映射成
     `Error::saved_pending_projection`，其余错误**原样返回**；而歌单编辑走
     `plan_library_edit`（`local_library_edit.rs:175-198`）传入的是 `None`。
     于是重试拿到的是裸 SQLite 错误，**没有稳定操作身份**，与
     `specs/playlist-management/spec.md`（LD-08）"目录已保存而投影失败 MUST 返回稳定操作身份
     及已保存待更新状态"直接冲突。
  2. **追赶修好后会撞唯一名索引**（代码确认）。投影恢复后重试：追赶成功 → 目录里已保存的创建
     进入投影 → 但规划阶段仍按 `application/playlist/durable.rs:73` 每次调用新铸一个
     `PlaylistId`，`statements::create_playlist`（`statements/operations.rs:43-52`）以该新 id 插入
     `playlists`；而 `migrations/0001_initial.sql:107` 有 `UNIQUE (library_root_uuid, normalized_name_key)`，
     由 `support.rs:35-42` 的 `map_constraint` 映射为 `Error::conflict("SQLite uniqueness constraint")`。
     该插入发生在规划事务内、目录提交之前，因此**不会产生第二个目录提交**，
     但已保存的创建对用户不可达，且被误报成"未保存的名称冲突"。

- **不是根因的地方**：`application/playlist/durable.rs:21-37` 的 `validate_name` 在重试时
  **通过**（第一次投影失败已回滚，SQLite 里没有同名行），所以上一版交接把它写成根因是不准确的；
  观测到的错误是协调器追赶的裸 SQLite 错误，不是 `"playlist name already exists"`。
- 首次尝试的身份没有丢：`application/library_commit.rs:50` 已把首次投影失败映射为
  `Error::saved_pending_projection(batch.operation_id, …)`。**丢身份的只有重试路径。**
- 违反 `specs/playlist-management/spec.md`："目录已保存而投影失败 MUST 返回稳定操作身份及
  已保存待更新状态，不得当成可直接重新创建的未保存失败"。
- 剩余工作：让这条用例由 RED 转 GREEN。`#[ignore]` 已经解除，**套件因此按设计是红的**。

#### 缺陷 1 的修复方案（本轮只做了只读核实，未实施）

1. **端口签名**：`crates/echo-core/src/application/ports/local_library_edit.rs:49-56` 的
   `create_library_playlist` 现在返回 `Result<(), Error>`，改为 `Result<PlaylistId, Error>`，
   让"已保存的那一次创建"的身份能回到应用层。
2. **从目录真相解析已保存的创建**：在 `crates/echo-core/src/domain/library/durability.rs`
   增加 `LibraryReplay::playlist_by_name(name) -> Option<LivePlaylist>`
   （`LivePlaylist { id: uuid::Uuid, display_name: String, operation: Option<LibraryOperationId> }`），
   按 checkpoint 记录 → commit 记录顺序扫描，后到的 `PortableRecord::Playlist` 覆盖前者，
   最新记录是 `Tombstone { deleted_kind: RecordKind::Playlist }` 的丢弃；名字用
   `playlist_name_key`（`domain/text.rs:100-102`，幂等）比较。
   选基线扫描而不是查 `playlists` 表：本 change 里目录才是真相源，查投影会依赖投影状态，
   并可能把既有的同名歌单误判成"已保存的创建"。
3. **协调器在规划前解析**：`local_library_edit.rs:227-271` 的 `plan_library_change` 已在
   第 231 行拿到 `baseline = durable.recover(root)`。若基线里已有同名且存活的歌单，则
   **不再铸新 `PlaylistId`、不再产出第二批**：直接返回已保存歌单的 id；空批次会走
   第 259-261 行的早退分支，因此**不会产生第二次目录提交**。
   若该 id 尚未出现在投影中，不得报普通成功：创建操作 id 已知时返回
   `Error::saved_pending_projection(creation_op, cause)`，否则
   `Error::unavailable("playlist", …)`。
4. **追赶失败映射**：`local_library_edit.rs:235-249` 改为——取基线中第一条
   `library_commit_seq > 水位 commit_seq` 的提交，用它的 `batch.operation_id` 映射为
   `saved_pending_projection`；播放事件的既有规则保持优先。水位来源是
   `durability_projection/validation.rs:28` 读的 `library_projection_watermarks.commit_seq`。
5. **计划闭包签名**：`plan_library_change` 的闭包需要看到 `&LibraryReplay`（基线）才能解析
   已保存的创建。当前签名是
   `FnOnce(&Connection, &dyn ControlPlanePort, LibraryId, u64) -> Result<(LibraryBatch, T), Error> + Send + 'static`，
   `&LibraryReplay` 只能作为**参数**传入（捕获会破坏 `'static`）。连带改动：
   `plan_library_edit`（175-198）的包装闭包、`infrastructure/sqlite/local_library_edit/playback.rs:21`
   这一个 `Some(session.as_uuid())` 调用点，以及
   `application/testing/memory_database/local_library_edit.rs:141-150` 的内存 fake
   （需同步改签名并补同样的重试用例）。
6. **应用层**：`application/playlist/durable.rs:70-79` 现在自己铸 `PlaylistId::new()`；
   端口改为返回 id 后，应用层必须用端口返回的 id，否则重试仍会返回新身份。
7. **待定的边界**：`validate_name` 在端口调用**之前**执行，修复后协调器内的追赶会先让同名行
   出现在投影里，因此**下一次**重试的 `validate_name` 会返回 `"playlist name already exists"`。
   要区分"本机已保存的创建"与"用户想创建一个已存在的歌单"，需要在实现时一并处理
