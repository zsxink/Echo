# 3.4 用户资源原件与实际受管版本位置持久化

日期：2026-10-26
分支：`codex/issue-72-library-first-durability`

## 1. 声明语义（已有实现，本轮补证据）

`batch.resources` 的每一项是 `DurableResource { relative_path, content_hash,
byte_length }`，语义是"**已经发布在资料库里的资源**"：adapter 在写 marker 之前
重验实际字节，声明与磁盘不符即拒绝整批提交，不会先去修复文件再接受声明。

允许的两类位置（`domain/library/durability.rs::LibraryBatch::validate`）：

| 类别 | 路径形式 | 附加约束 |
| --- | --- | --- |
| 用户资源原件 | `echo/assets/<blake3>` | `relative_path` 必须逐字等于 `echo/assets/<content_hash>`，即地址就是内容摘要 |
| 受管媒体版本 | `echo/media/<kind>/<owner-uuid>/<declaration-digest>/<logical-path>` | 接受全部 `echo/media/` 前缀；声明摘要版本由 publication 侧校验 |

其余 `echo/` 下的控制面路径（`echo/state/*`、`echo/records/*`、`echo/media` 目录本身）
不是资源来源，直接以 `resource is not media or an immutable asset` 拒绝；
`content_hash` 不是 64 位小写十六进制时以 `resource requires a BLAKE3 digest` 拒绝。
`echo/tmp/` 永远不是资源来源（staging 只在 publication 的 journal 中被引用）。

`assets::validate_resource` 在 `transaction.rs` 中先于 `publish_prepared` 和 marker
执行，因此任何一项不可验证的声明都不会留下 prepared 正文、marker、operation 状态
或链上提交——调用方只能看到一次明确的拒绝，而不是"已保存待恢复"。

## 2. 不写源音乐字节

Echo 从不写回音乐文件标签。`infrastructure/metadata/tags/mod.rs` 只读解析，
doc 明确"The original file is never modified"；`rg -n 'save_to_path|write_tags|set_tag'
crates/` 在生产代码中 0 命中，唯一命中是 `metadata/tags/tests.rs:239` 的 fixture
构造器。外部工具改写标签后，扫描与监听都以**重新读取的字节**为准：

- `watch.rs::parse_file_event` 强制 `force_content_check = true`，不信任
  size+mtime 变化启发式；
- 重新计算 BLAKE3 后以同一 `Song` UUID 与 `added_at` 提交新的 after-image，
  资源声明改为外部产生的新摘要；
- 若外部修改后文件不可读/不可解析，只影响本机可用性，不删除对象与关系。

## 3. 本轮新增证据

### `durability/tests/resources.rs`

| 测试 | 验证的规格条款 |
| --- | --- |
| `library_durability_unverifiable_managed_version_is_refused_before_any_evidence` | 长度不符与"同长度不同字节"两种篡改都被拒；拒绝发生在 marker/prepared/operation 状态之前，链上无提交；磁盘上的字节**保持被发现的样貌**，Echo 不为了迎合声明而重写或"修复"媒体 |
| `library_durability_missing_managed_version_is_never_synthesized` | 声明指向不存在的受管版本时返回 `io` 错误，不创建占位文件、不留证据 |
| `library_durability_tampered_user_original_is_refused_and_kept_for_diagnosis` | 内容寻址原件被改写后，提交以 `durable resource hash mismatch` 拒绝；读取侧以 `immutable asset is corrupt` 报告同一事实；篡改后的字节保留作为诊断证据；非规范地址在解析路径前即 `invalid asset hash` |
| `library_durability_resources_must_name_media_or_an_exact_original` | 控制面路径（`echo/state/*`、`echo/records/*`、`echo/media` 目录）不是资源；原件路径必须与自己的摘要对应；摘要必须是小写十六进制；三类"无地址"声明一律拒绝 |
| `library_durability_managed_version_declaration_survives_checkpoint_and_fresh_rebuild` | 原件与受管版本同批提交后：`read_operation` 返回冻结声明 → 强制压缩后覆盖镜像仍含每条 `DurableResource` → 用回收后目录重建**全新 SQLite**，`read_recovery_records` 逐字段（路径/哈希/长度）读回同一集合 |

## 5. 边界

- 覆盖原件的专属规则（`cover_asset` 必须与 `echo/assets/<hash>` 声明成对出现）归
  6.2，已在 `change_set.rs::validate_against` 落地。
- 远端媒体的 owner/version 校验归 7.4；本任务只证明"实际位置 + 长度 + 哈希"可从
  目录声明恢复，不代替 publication v2 的 owner 归属与旧声明摘要校验。
- 本任务不新增删除能力：受管版本与原件由 3.5 的"GC 不删字节"承诺保护。
- 测试使用真实临时目录与注入 hook，覆盖 POSIX 语义；Windows/Linux 原生认证仍属 9.3。
