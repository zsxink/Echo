# Task 4.3: disposable projection validation and root replacement

Date: 2026-10-26 (final revision)

## Implemented

- Reconstructs a disk-backed candidate SQLite database from verified directory replay, without reading the active projection as source data. The candidate lives in an owner-only private directory and is always removed, including on failure.
- Rejects a replay whose library identity differs from the manifest; verifies replay head, SQLite `quick_check`, foreign keys, exact typed retained records/state/resources, and no candidate upload mutations/outbox.
- An incremental projection failure can fall back to a rebuild only after the current manifest and directory head match the replay being adopted.
- Replaces root-owned songs, playlists, scan runs, search rows, artist covers, projection watermark, applied operations, and retained evidence within one writer transaction. A failed SQL write, a failed final `COMMIT` (deferred foreign key), or a read-only database rolls the deletion and replay back together and leaves the previous projection in place.
- Preserves other roots and blocks while local file operations are incomplete.
- **Sync-context roots are now rebuilt, not refused.** Protocol rows are root-scoped directory evidence rather than a projection of the read model: no protocol table has a foreign key to `songs`/`playlists`, and only `retry_library_sync_state` may re-project protocol facts under a validated live session. LD-07 requires a rebuild to keep unconfirmed intent and conflicts, so the rebuild snapshots the selected context plus the row count of all 19 live and 19 archived protocol tables before the deletes, compares after projection, and rejects the whole transaction if anything moved.
- **A globally corrupt SQLite file is quarantined before it is ever read.** `SqliteDatabase::open` renames the damaged file and its WAL/SHM companions to a unique same-directory name (byte-for-byte, never read, repaired, or deleted), then starts a fresh migrated projection. Damage classification is deliberately narrow: a held write lock, a read-only volume, a missing permission, or a released-migration checksum mismatch still fails the open and leaves the file where it is, because that projection is still usable.

## Remaining boundaries (outside 4.3)

- Native cross-platform acceptance of the filesystem and quarantine paths is 9.3/9.7, not 4.3.
- Whole-application cold start replays a library projection only after the user selects a root; there is no silent auto-adoption of an unselected root.
