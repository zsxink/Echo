### 1. 新增模块 `application/delete/intent.rs`

复用了既有的领域类型 `LocalDeleteIntent`（`domain/sync.rs:719-827`，此前无任何使用者）：
`intent_id` / `final_mutation_id` / `object` / `created_at_ms` / `undo_deadline_ms` / `state`，
`UNDO_WINDOW_MS = 10_000`，`begin()` 铸两个身份，`resolve(action, now_ms)` 是纯状态机。

模块职责与关键决定：

- **提交载体是未限定作用域的目录状态**：
  `DurableStateChange::new(StateKind::DeleteIntent, operation.as_uuid(), payload)`。
  理由是删除意图是本机证据、不授予发送权限，不应进入 authority 作用域；
  `StateKind::DeleteIntent` 的目录名为 `delete-intents`（`domain/library/durability.rs:76`），
  物化为 `echo/state/delete-intents/<uuid>.json`。
  `StateTarget` 没有 delete-intent 变体，所以只能用未限定作用域形态。
- **转移身份确定化**：`transition_id(operation, stage)` 用 blake3 派生每个转移的 `operation_id`。
  同一转移重试命中提交去重（同 operation_id + 同 payload ⇒ `SavedPendingProjection`），
  不会触发 `operation identity reused with another payload` 冲突，也不会追加第二个事实。
- **意图身份 = 操作身份**：`begin` 把 `intent.intent_id` 覆写为操作 UUID，
  与 SQLite `sync_local_delete_intents.intent_id = operation.to_string()` 对齐。
- **幂等**：`begin` 先 `load` 已提交意图，命中即原样返回，绝不铸第二个（否则终态被拆成两个）。
- **`load` 的失败语义**：replay 中取同一 id 的**最后一条**（seq 最大）；payload 不可读是错误，
  不能静默当作"没有意图"。
- **撤销/终结竞争由目录裁决**：`cancel` 对 `Finalized` 报
  `conflict("delete intent already finalized; the object is gone")`，
  对 `SupersededByRemoteTombstone` 报 `conflict("a confirmed remote tombstone already removed the object")`；
  对已 `Cancelled` 的重试直接 `Ok(())`。

### 2. 删除入口先写意图、再隐藏

`application/delete.rs:158`：`DeleteSongs::delete` 在 hide 事务**之前**调用 `intent::begin`。
这样"意图已提交、hide 未提交"的崩溃窗口正是恢复路径能看见的形态；
反过来（先 hide 后意图）会留下一个隐藏歌曲、而意图只存在于 hide 本该写入的那张表里。
取回的 `final_mutation_id` 随即通过 `tx.set_undo_deadline(operation, deadline, final_mutation_id)`
（`delete.rs:185`）传进 hide 事务。

### 3. 撤销先取消意图，再让歌曲可见

`application/delete.rs:324`：`RestoreDeletedOperation::restore` 在逐个 `restore_resource` 之后、
`set_song_availability(Available)` 事务之前调用 `intent::cancel`。
顺序是刻意的——被终结或已被远端墓碑取代的意图必须在歌曲重新可见**之前**拒绝撤销。

### 4. 崩溃恢复的 hide 同样先写意图

`application/recover/mod.rs:621`：`hide_operation` 不再忽略 `root`，先 `intent::begin`（幂等），
再用同一 `final_mutation_id` 走 `set_undo_deadline`（`:647`）。
"意图已写、hide 未写"的崩溃正是这条路径要恢复的形态，第二次尝试复用已提交身份。

### 5. 身份贯通到 SQLite

`application/ports/transaction.rs:114`：`TxOperationWriter::set_undo_deadline` 新增
`final_mutation_id: MutationId`，文档说明它是目录意图已冻结的身份。

`infrastructure/sqlite/tx_impl.rs:118`：`sync_local_delete_intents` 的

   `application/trash.rs:311-366` 的 `finalize_persisted_trash` 先 `tx.delete_song(song)`（`:345`）

   物理终结后意图仍停在 `Open`。

   那两处只允许"已持久化 TrashApplied 收据支撑的数据库前滚"，
   所以接线时必须确认目录提交走的是控制面（`deps.control`）而不是 `deps.fs`。
