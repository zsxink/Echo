## Why

桌面端删除歌曲后，文件只会留在 Echo 的 `echo/tmp/trash/<operation-id>/` 暂存目录：生产组装点没有接入任何真实系统回收站后端，且过期删除只在启动恢复阶段尝试最终化。这样用户在不重启应用时无法在系统回收站找回文件，重启后也可能因后端缺失而永久滞留在内部暂存区，违背现有产品文案与删除规格。

## What Changes

- 接入跨 macOS、Windows、Linux 的真实系统回收站适配器，将已过撤销窗口的 Echo 删除暂存目录交给操作系统回收站。
- 保留现有 `TrashPending → TrashApplied → DatabaseFinalized` 安全边界：只有真实后端明确成功才清理歌曲记录；失败或结果不确定时保留可恢复证据并按既有规则重试/隔离。
- 增加桌面会话内的过期删除调度，使应用不重启也会在撤销窗口结束后执行最终化，并在运行期间周期性重试暂时失败的系统回收站调用。
- 为真实后端增加路径解析与防护，只允许由已绑定资料库根目录解析出的 Echo 自有删除暂存目录进入系统回收站。
- 补充跨平台适配单元测试、会话内调度测试和原生回收站验收说明。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `library-experience`: 删除歌曲在撤销窗口结束后必须于当前会话内进入系统回收站；真实回收站调用失败时继续遵守既有重试、结果未知和写保护语义。

## Impact

- 受影响模块：`echo-desktop` 平台回收站适配与运行时生命周期、桌面 Tauri 组装点；`echo-core` 仅复用既有 `SystemTrashPort` 和最终化用例，不引入平台依赖。
- 新增桌面层跨平台依赖 `trash`，并更新 `Cargo.lock`。
- 不改变 Core 公共删除 API、SQLite schema、可携带控制面格式、10 秒撤销窗口或同步墓碑语义。
- 不包含永久删除、系统回收站浏览/恢复 UI、移动端实现或修改用户原始未受管文件的能力。
