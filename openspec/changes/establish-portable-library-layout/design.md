## Context

现有 Core 已将本机绝对根目录绑定在 desktop runtime，并在 SQLite 保存歌曲 UUID、相对路径、播放列表和 `sync_outbox`。当前导入目标仍是根目录下的艺人目录；项目设计已确定远端只存媒体和版本化 JSON，绝不直接同步 SQLite。见 proposal.md 与本 change 的规格。

本设计将“可携带资料库”作为媒体与版本化对象资料的组合，而 SQLite 保持每台设备的查询投影和运行时真相源。实现属于 `echo-core` 的 Domain/Application/Infrastructure 边界：领域对象和同步载荷不依赖文件系统或 UI；文件布局、SQLite 和将对象资料持久化的适配器由 Infrastructure 实现；导入、扫描、恢复和未来同步用例经 Ports 协调。

## Goals / Non-Goals

**Goals:**

- 使受 Echo 管理的媒体拥有单一、稳定且跨平台的 `media/` 根。
- 固化可供未来 S3/WebDAV 传输的对象资料形状，确保全新设备可不依赖另一设备的 SQLite 恢复资料库状态。
- 让相对路径、UUID、BLAKE3 和墓碑在导入、扫描、崩溃恢复与跨设备重建中保持一致。
- 保持一期离线、无账号、无远端连接和无同步 UI 的范围。

**Non-Goals:**

- 不在本 change 实现 S3、WebDAV、认证、上传、下载、冲突 UI 或移动端。
- 不同步 SQLite、封面缓存、播放队列、主题、绝对路径或设备凭据。
- 不迁移、扫描或保留旧资料库布局中的歌曲记录；用户以新资料库和重新导入替换旧资料库。
- 不提供歌曲编辑、歌单手动排序或实时协作式冲突体验。

## Decisions

### 1. 资料库采用媒体面、控制面与本机面分离

资料库根目录固定为：

```text
<library-root>/
  media/<artist>/<artist> - <title>.<ext>
  echo/manifest.json
  echo/records/<kind>/<prefix>/<uuid>.json
  echo/tmp/<operation-id>/
```

`media/` 是唯一由 Echo 管理的发布目标；可见的 `echo/` 是资料库控制面，`echo/tmp/` 仅供本机导入恢复并且不会被扫描或同步。应用数据目录继续保存 SQLite、同步凭据、游标和可再生缓存。

选择此布局而非同步 `echo.db`，是因为 SQLite WAL、锁、平台路径和本地缓存都不是跨设备合并格式。选择资料库内可见控制面而非只在远端保存 JSON，是因为资料库可整体移动、备份或由文件同步工具复制，且新设备可发现其逻辑身份。控制面不保存任何秘密，因此可安全进入用户选定的同步资料；`echo/tmp/` 始终是本机恢复工作区，不属于同步资料。

### 2. 每个可同步逻辑事实以独立、分片的对象资料表示

manifest 持有 `formatVersion` 和 `libraryId`。对象记录以 UUID 的前缀分片，避免单目录在大曲库下包含过多条目。对象类型为 `song`、`favorite`、`playlist`、`playlist-item`、`override` 和 `tombstone`。歌曲记录包含 `mediaPath` 与 `contentHash`；歌单成员是独立对象，带 `playlistId`、`songId` 和追加顺序键。

每项都包含 UUID、对象类型、`revision`、`updatedByDeviceId` 和混合逻辑时间（HLC）。本机对同一对象保持 revision 严格递增；未来跨端使用 HLC、设备 ID、对象 UUID 的稳定顺序执行最后写入者裁决，而不依赖墙钟。对象资料是 `sync_outbox` 全量载荷的持久化表示；两者在同一用例的 Unit of Work 中更新，跨越媒体文件发布时由 `operation_journal` 处理恢复。

备选方案是一个同步 SQLite 文件或单个巨型 JSON 快照。前者无法安全合并，后者会让并发修改和部分失败把整个曲库变为冲突单位；按对象记录能局部重试、墓碑传播并支持增量上传。`snapshot.json` 仅可作为从 records 导出的加速缓存，损坏或缺失时必须可重建，不能是唯一事实来源。

### 3. 路径只描述文件定位，内容哈希与 UUID 描述身份

所有协议、数据库跨层 DTO 和对象资料中的路径均使用相对于资料库根目录的 `/` 分隔规范化相对路径，例如 `media/周杰伦/周杰伦 - 晴天.flac`。路径必须拒绝空值、绝对路径、`..` 跳出根目录和控制面目录。播放实际路径只由平台层的 root registry 解析。

导入产生目标文件名后不因覆盖层或标签更新而自动重命名，以免制造同步移动风暴。扫描发现移动或改名时，仍先用 BLAKE3、再用既有弱音乐键规则重关联 UUID；同步来的记录在媒体未到达时成为 missing，而不能因此另建歌曲。

### 4. 新设备以“拉取对象资料 → 投影 SQLite → 扫描媒体”恢复

未来设置同步用例先读取 manifest，校验格式与 library ID，拉取全部对象资料和墓碑，应用确定性冲突裁决并在本机事务中投影歌曲、收藏、歌单、成员和覆盖层。随后扫描 `media/`，以相对路径找到文件并复核内容哈希。缺失的媒体保持现有 UUID 与关联，待媒体传输完成后恢复可用。

该顺序避免“媒体先扫描”时为同一文件随机分配新的 UUID，也能在媒体和元数据不同步到达时展示一致的歌单。二期连接器遵循 Strategy + Adapter 的 `RemoteConnector` Port；S3/WebDAV 仅负责传输 manifest、对象资料与媒体，不参与领域合并。

### 5. 资料库布局整体切换，不保留旧布局兼容

新的受支持资料库只扫描 `media/`，并将 `echo/` 作为控制面。既有根目录艺人文件夹和既有本机歌曲 UUID 不迁移、不扫描、不自动移动；用户通过选择或建立新资料库并重新导入媒体替换旧资料库。新资料库首次写入时初始化 `echo/manifest.json` 与相应对象资料。

## Risks / Trade-offs

- [对象资料与 SQLite/媒体文件无法构成单一原子事务] → 扩展 `operation_journal`，记录预留 UUID、预期哈希、路径、对象资料阶段；启动恢复按完整媒体补写资料或清理未发布暂存物。
- [文件同步工具可能暂时暴露半写 JSON] → 每个对象先在同目录临时文件写入、校验后原子 rename；读取端忽略临时文件及不完整/版本不支持记录并在下次同步重试。
- [两台设备并发改同一对象] → 从本 change 起持久化 HLC 与设备 ID，未来统一 LWW 规则；歌单成员独立对象可避免整个歌单互相覆盖。
- [大曲库产生大量对象文件] → UUID 前缀分片、增量写入；只将可再生 `snapshot.json` 用于冷启动加速，不在热路径反复生成。
- [用户误选旧资料库] → 根目录缺少可扫描的 `media/` 时明确要求建立新资料库或重新导入，不尝试迁移或猜测旧歌曲身份。

## Migration Plan

1. 新增顺序 SQLite 迁移，为可同步对象补充写入设备/HLC和歌单成员稳定 UUID；不得修改已发布迁移。
2. 在 Core 增加资料库布局、路径验证和可携带对象的领域类型与 Ports；让 SQLite/文件系统适配器分别实现投影与对象资料读写。
3. 修改导入计划和恢复日志，使新发布文件进入 `media/`，并在发布后原子物化歌曲资料与 outbox。
4. 修改扫描/监听，仅发现 `media/` 并过滤 `echo/`；当根目录缺少 `media/` 时报告需要建立新资料库或重新导入，不迁移旧文件或旧 SQLite 歌曲资料。
5. 为新设备恢复用例准备导入/投影接口与端到端夹具，但不装配网络连接器或 UI。
6. 发布后若需回滚代码，保留 `media/`、`echo/` 和 SQLite 迁移数据；旧版本可继续扫描 `media/` 内音频作为普通子目录，升级版本可再次完成资料物化。禁止自动删除控制面或移动用户文件作为回滚步骤。
