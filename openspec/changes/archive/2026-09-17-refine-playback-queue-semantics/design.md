## Context

参见 [proposal.md](proposal.md)。桌面播放器已将队列限定在 `echo-desktop` 平台层：`Queue` 保存 entry、当前位置、历史和随机轮次，`PlaybackCoordinator` 是传输命令和播放器适配器之间的状态机，Tauri 仅转发类型化命令并发布快照。当前实现虽然有队列投影和三种模式，却将“下一首播放”直接插入当前项之后，连续操作会倒序；队列投影没有完整的循环顺序或展示元数据。

## Goals / Non-Goals

**Goals:**

- 让一个明确的、可持久化的队列状态机决定全部导航与面板顺序。
- 在单一快照中交付 UI 所需的 entry 元数据，避免 React 根据歌曲 ID 拼装或猜测队列顺序。
- 保持平台分层：播放队列、会话和 mpv 适配仍位于 `echo-desktop`，Core 与 React 都不拥有播放规则。

**Non-Goals:**

- 不新增拖拽排序、移除单项、跨设备同步队列或移动端播放实现。
- 不改变播放统计、临时项持久化边界、资料库歌曲 UUID 或播放器引擎。
- 不在本设计中定义新的视觉风格；只落实队列面板的八行可视区域、滚动和元数据显示所需的行为。

## Decisions

### 以规范化播放投影作为唯一 UI 队列

`Queue` 保留内部的规范条目顺序、当前 entry、历史、随机轮次和下一首优先区；`PlaybackCoordinator` 根据当前模式产生 `current + up-next` 的规范化投影。投影在一个列表循环内从当前项之后走到尾部再回绕至头部，因此每个其他可播放 entry 正好出现一次；随机模式按优先区、随机包、下一轮候选顺序投影；单曲循环仍显示当前项和待播项，但自然结束不消费待播项。普通与沉浸模式共同消费同一投影，并以普通模式现有尺寸 token 作为唯一尺寸来源，避免浮层在切换模式后产生不同的行数或条目尺度。

这使面板、播放栏数量和 IPC 事件读取同一个事实来源，也避免 UI 将内部的历史区段误渲染在当前项之前。替代方案是在 React 侧把当前项移动到第一位并重排列表；它无法可靠处理随机包、回绕、重复歌曲和恢复，故不采用。

### 从视图开始播放是替换而非追加

曲库、歌单、收藏和搜索等视图的歌曲点击统一调用“替换播放上下文”：由桌面端根据视图标识、筛选和排序解析完整结果，前端只提交被选歌曲或其稳定定位信息，不能提交歌曲 ID 分页或可篡改的部分列表。该完整结果新建 queue entry，选择项设为当前，同时清除原队列、下一首优先区、随机包和旧上下文状态。队列成员数因此严格等于该视图的歌曲数；新投影在列表循环中从当前项向后并回绕呈现全部成员。

“加入播放队列”和“下一首播放”是唯一在现有上下文追加 entry 的操作。将视图点击做成追加会让用户无法通过播放歌单获得确定的队列边界，也会残留旧队列中的手动项，故不采用。

### 将“下一首播放”建模为稳定的 FIFO 插入区

新增 entry 同时成为队列的稳定成员，并插入当前位置后的连续优先区尾部，而非每次都插入当前位置。优先区以 entry ID 表示，连续请求 A、B、C 的消费顺序固定为 A、B、C；消费、清空、删除、失败跳过和恢复都会从该区同步移除或重建有效 ID。所有“下一首”决策先检查该区，再进入模式自身的顺序。

物理插入而不是仅在 UI 保存一个临时列表，能让列表循环在 A、B、C 后自然回到原来的后继项，并保持 queue entry ID、重复歌曲和会话恢复的一致性。仅将每次新增项插到 current 后会将连续操作反转，故不采用。

### 用显式导航意图区分自然结束与手动跳转

协调器把“自然结束”“手动下一首”“手动上一首”和“错误跳过”作为不同状态机事件，而不是让所有入口共用一个 `next` 分支。列表循环的前后项使用规范列表位置并回绕，但只有自然结束和手动下一首先消费优先区；手动上一首绝不消费或重排优先区。随机播放仅为前进消费随机包，上一首继续使用有效播放历史；单曲循环只对自然结束重载当前 entry，手动下一首临时采用列表循环的前进规则而不改变用户选定的模式。错误跳过保持现有的失败轮次保护，并绕过单曲重复。

这比临时切换播放模式再复用现有 next 方法安全：临时切换会污染模式快照、随机包或后续行为。状态机仍由协调器（Command / State Machine 模式）拥有，Tauri command 不包含选择逻辑。

### 将队列展示信息随快照提供，并用受控查询补齐资料库元数据

队列 entry DTO 扩展为标题、艺人、时长和封面引用（或明确的空值）；桌面层在构建/发布快照时由资料库查询服务按 song UUID 解析数据，临时项沿用已解析的会话元数据。UI 只渲染 DTO 和封面缓存，不再以“资料库歌曲”或通用标题代替真实条目。为避免每次播放器时间更新触发 N 次查询，元数据解析必须按 entry/song 进行缓存、批量化或仅在队列内容变更时刷新。

替代方案是前端对每行执行独立 `song_detail` 调用；这会造成滚动时的请求瀑布、短暂错误内容和与队列快照不一致的状态，故不采用。

### 版本化会话以恢复新队列状态

持久化会话升级版本以保存下一首优先区（以及已有的 entry、当前项、历史和随机包）。恢复读取旧版本时，将其视为没有优先项，保留现有安全过滤、暂停恢复和临时项不持久化规则；未知未来版本继续安全地不恢复。迁移不涉及 SQLite 或 Core 数据。

## Risks / Trade-offs

- [循环投影会包含已播放但将在回绕后再播放的项] → 以“当前 + 下一首实际顺序”的单轮投影保证面板与列表循环一致，并为回绕和重复歌曲写 entry-ID 级测试。
- [优先插入、随机包、删除和失败集合可能包含失效 ID] → 所有消费与恢复路径过滤不存在、blocked 或失败的 ID；每个队列突变后验证不变量。
- [扩展快照元数据可能增加事件负载和查询开销] → 队列结构变更时缓存/批量解析元数据；高频位置事件复用最近的队列 DTO。
- [会话 JSON 版本变化] → 仅新增向后兼容字段，旧会话默认空优先区，并测试版本迁移和恢复后不自动播放。

## Migration Plan

1. 为队列状态和持久化会话实现新结构与反序列化兼容，先覆盖不变量和模式矩阵单元测试。
2. 更新协调器、Tauri command/snapshot DTO 和事件发布，使所有传输入口使用显式导航意图。
3. 更新 React 类型和队列面板，限制列表视窗为 8 行、在普通与沉浸模式复用同一尺寸 token，并显示快照元数据；添加组件测试与端到端回归。
4. 以歌单/搜索/收藏视图的队列重建、旧优先区清除、旧会话、重复歌曲、blocked/failed entry、空队列和三种模式进行恢复及回归验证。若部署后需要回退，代码可忽略新增会话字段并按旧会话规则恢复；新会话数据不会影响资料库或歌单。
