## Context

参见 proposal.md 的 Why 和 specs/library-experience/spec.md。资料库的全部歌曲、收藏和搜索由 Core 提供 keyset 分页；近期视图最多 100 首，歌单详情当前返回完整成员，歌手/专辑详情已有聚合计数。

## Goals / Non-Goals

**Goals:** 分页查询同时提供匹配完整结果数，让列表标题不依赖已加载页面；计数复用与歌曲查询相同的资料库、可用性、收藏和搜索筛选。

**Non-Goals:** 不改变分页游标、每页大小、近期视图 100 首上限、歌单加载策略或目录聚合策略；不增加数据库迁移。

## Decisions

- 在 Core 的通用 `Paged<T>` 增加匹配总数。SQLite 在一个只读 WAL 快照事务中，使用相同的视图与搜索条件执行 `COUNT(*)`，但不加入游标谓词；同一事务也读取根目录版本、游标排序键和歌曲页，避免并发写入让总数、页内容和返回游标描述不同的目录状态。内存目录实现保留截断前的数量，作为测试/替身语义的一致实现。
- 通过现有分页 DTO 将总数传递为 `totalCount`，由桌面 UI 在查询完成后保存并显示。近期视图直接以其最多 100 首的查询结果计数；歌单和聚合详情继续采用当前完整成员/后端聚合数据。
- 这是同版本桌面端与 Tauri 后端间的 IPC 加字段，无数据库格式变化。生成 TypeScript 合约与其生成器同步更新；UI 对旧 fixture 缺字段保留安全回退。

## Risks / Trade-offs

- 每次分页请求多执行一次 COUNT 查询 → 计数准确且独立于 cursor；分页使用的筛选谓词复用，避免视图口径漂移。
- 搜索计数可能增加 FTS 查询成本 → 仅在用户请求歌曲查询时计数，不新增独立的全库扫描或前端跨页累计。

## Migration Plan

不需要数据迁移。升级时桌面端与 Tauri 后端作为同一应用版本发布；若需回滚，回退应用二进制和代码即可，持久化数据不变。
