## MODIFIED Requirements

### Requirement: 多选导入与默认目标命名

系统 MUST 提供一次选择多个本地音频文件的导入操作，并逐文件处理。每个文件解析标签后，目标目录 MUST 使用 `media/歌手/歌手 - 歌曲名.原扩展名`；缺少歌手或歌曲名时 MUST 使用可见且确定性的兜底名称（分别为“未知艺人”和“未命名歌曲”），路径组件和文件名 MUST 清理平台禁止字符、控制字符和保留名称，同时保留可辨识性。

#### Scenario: 多选文件成功导入
- **WHEN** 用户选择多个支持格式的外部音频并确认导入
- **THEN** 系统分别解析、复制并返回每个文件的成功、跳过或失败结果，单个文件失败不回滚其他已成功文件

#### Scenario: 标签缺失和非法字符
- **WHEN** 音频缺少歌手/歌曲名或标签包含 `/`, `\\`, 控制字符、平台保留名或过长路径组件
- **THEN** 系统按兜底规则和字符清理规则生成 `media/` 下的目标路径，截断时仍保留扩展名和可区分的稳定后缀，且不覆盖任何既有文件

### Requirement: 暂存、校验、原子移动与操作日志

导入 MUST 先写入资料库内专属 `echo/tmp/<operation-id>/` 下的暂存位置，完成文件大小/可读性、BLAKE3 和必要的元数据解析校验后，才发布音频及其侧车文件；每个文件自身 MUST 通过同文件系统 rename 原子发布，音频是主资源，系统不宣称两个独立目标文件能跨文件原子提交。SQLite 歌曲记录及相应可携带对象资料 MUST 仅在音频完整发布后以单个可恢复事务提交。系统 MUST 为每个导入及每个资源记录可恢复的意图态、结果态、路径和预期哈希，禁止产生指向未完成文件的歌曲记录。

#### Scenario: 校验失败不落库
- **WHEN** 暂存文件复制不完整、哈希不匹配、标签解析失败到无法建立歌曲或最终移动失败
- **THEN** 系统不创建歌曲记录或可携带歌曲资料，不覆盖目标文件，保留可诊断失败结果并清理或标记暂存文件以便恢复

#### Scenario: 导入成功原子可见
- **WHEN** 暂存音频及同名 LRC（若存在）均通过校验并移动成功
- **THEN** 系统提交歌曲记录、相对路径、哈希及对应可携带资料，用户只能看到完整目标文件，不会看到半复制文件作为可播放歌曲

#### Scenario: 崩溃后恢复
- **WHEN** 应用在暂存、移动或 SQLite/可携带资料提交之间崩溃并再次启动
- **THEN** 系统读取操作日志，补写缺失且已完整落地的记录或回滚未完成文件，清除不可用暂存物；恢复过程可重复且不产生重复 UUID/文件

#### Scenario: 音频发布后侧车失败
- **WHEN** 音频已经完整原子发布，但同名 LRC 在发布前后失败或应用崩溃
- **THEN** 系统允许以同一预留歌曲 UUID 完成音频入库，并恢复、重试或清理 LRC 子资源；结果明确标示歌词失败且不得留下半写侧车

#### Scenario: 发布后 watcher 抢先观察
- **WHEN** 导入已经把完整音频发布到最终路径，但 watcher 在导入数据库提交前观察到该路径
- **THEN** watcher 必须等待活动导入的路径 claim 或复用其预留歌曲 UUID，最终只能产生该预留 UUID 对应的一条歌曲记录
