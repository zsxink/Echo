## Context

见 `proposal.md` 的动机。本地资料库目前以歌曲分页和歌曲封面为中心；`library-experience` 仅定义歌曲资料库视图，而桌面 UI 也尚未拥有歌手、专辑或歌手封面的领域读取模型。新视图必须保持 Core → Tauri → React 的依赖方向，不能由 WebView 聚合或持久化资料库事实。

## Goals / Non-Goals

**Goals:**

- 在 Core 提供与当前活动根隔离、可分页且确定性的歌手/专辑聚合和详情歌曲查询。
- 用独立的歌手封面覆盖层持久化用户选择，并以同一封面解析管线提供自定义、继承和占位三种来源。
- 在 React 资料库工作区中把目录、详情歌曲页、搜索、刷新和根切换纳入同一查询生命周期。

**Non-Goals:**

- 不编辑歌曲内嵌标签、不写回音频文件，也不在本变更中新增歌手简介、发行日期编辑或专辑编辑。
- 不为聚合目录引入新的全选或批量操作语义；详情歌曲列表复用既有全选、批量操作、远端同步协议和移动端范围。
- 不把歌手或专辑当作独立可播放的队列实体；播放仍由歌曲 UUID 驱动。

## Decisions

### 1. 在 Core 派生聚合，而不是在 React 合并分页歌曲

在 `echo-core` 的资料库查询边界增加歌手目录、专辑目录以及按聚合身份列出歌曲的用例和 DTO。聚合只读取当前根的 `available` 歌曲，按已生效的歌曲元数据归类；专辑键使用规范化专辑名，目录显示保留原始的生效展示值，代表歌手取最近加入的成员。所有目录查询都返回稳定身份、歌曲数量、封面候选和确定性排序键。

这遵守 Repository/Query 用例边界：SQLite 聚合和过滤留在 Infrastructure，Application 定义读取契约，Tauri 只转发类型化 DTO，React 不依赖数据库字段或自行合并无限歌曲行。替代方案是在 UI 加载全部歌曲后聚合；它会破坏大曲库性能、无法给出权威计数，并在根切换时更容易显示过期结果，故不采用。

### 2. 显式持久化歌手封面覆盖层，专辑封面保持派生

新增以 `(library_root_id, normalized_artist_key)` 为身份的歌手封面覆盖记录，保存与既有封面存储兼容的受控封面引用、版本和更新时间；通过顺序 SQLite migration 建表和索引。写入必须在 Application 用例的单个事务中完成，并通过既有对象资料/outbox 机制保留未来同步所需的可携带事实，但本变更不发起网络传输。

专辑不会新增可编辑实体：其封面从该专辑歌曲的当前有效封面确定性选出。歌手封面解析顺序为“已确认的歌手覆盖 → 最新专辑封面 → 占位封面”。“最新”取该专辑歌曲的最近成功添加时间，最终以稳定专辑键打破平局。该策略不依赖当前资料库尚未保存的发行日期元数据，仍可在本地曲库中稳定工作。

替代方案是把歌手封面伪装为某首歌曲的封面覆盖层，或只存 WebView 临时状态。前者会错误改变歌曲元数据，后者会在重启和跨设备接续后丢失，因此不采用。

### 3. 为聚合浏览定义显式的资料库导航状态

桌面资料库状态扩展为歌曲视图、目录视图和聚合详情三类互斥状态；详情持有 Core 返回的稳定聚合身份，而不是名称字符串的临时匹配。搜索、根 ID、请求代号和失效控制与现有歌曲查询共用：任何视图、搜索或根变化均取消/忽略旧请求并清空歌曲多选。

歌手和专辑目录复用同一目录卡片/行组件，详情复用歌曲列表的播放、收藏、单曲菜单和既有全选/多选能力；目录入口明确关闭并隐藏选择模式。替代方案是把详情伪装为全局“全部歌曲”的搜索过滤；这会丢失返回语义、封面标题和稳定聚合身份，故不采用。

### 4. 覆盖更新触发受控的局部失效

扫描提交、导入、歌曲元数据/封面变更、歌手封面写入与根切换都会使关联目录、详情和导航计数失效。UI 在新数据提交前保留最近成功的同一根结果；写入失败只保留权威结果并反馈错误。封面二进制或文件访问仍由 Core/桌面适配层处理，WebView 仅接收受限的显示引用，不读取本地路径。

## Risks / Trade-offs

- [歌曲标签缺少封面] → 使用最近成功添加时间和占位封面，并在 DTO 中保留封面来源以便诊断。
- [不同专辑的展示名称或大小写差异被错误拆分] → 在 Core 使用规范化专辑名聚合键，在 UI 使用稳定身份；测试 Unicode、大小写和同名专辑场景。
- [目录与歌曲列表在扫描/根切换时显示过期结果] → 所有请求携带根与查询代号，提交前校验当前上下文，并在 Core 返回确定性快照。
- [新封面记录影响本机重建或未来同步] → 使用顺序 migration、对象资料投影和 migration/恢复测试；失败时保持旧记录可读。

## Migration Plan

1. 添加向前迁移以建立歌手封面覆盖记录及其根、歌手键索引；既有资料库没有记录时按继承/占位逻辑读取，无需重扫。
2. 部署后先启用只读聚合查询，再启用覆盖写入和 UI；新增 IPC 使用新命令/DTO，不改变既有歌曲列表命令的返回格式。
3. 回滚时停止调用新增命令即可；迁移保留但不影响已有歌曲、歌曲覆盖、歌单或播放队列的读取。
