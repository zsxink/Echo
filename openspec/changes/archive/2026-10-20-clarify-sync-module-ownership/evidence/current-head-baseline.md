## Owners, paths and consumers

- Core domain/application remain transport-independent. The SQLite adapter root is `crates/echo-core/src/infrastructure/sqlite/mod.rs`; it owns `SqliteDatabase` (`writer`, bounded `readers`, path and device identity), actor/connection/schema/migration lifecycle. Sync implementations are declared at SQLite root across `sync.rs`, `sync_apply.rs`, `sync_baseline.rs`, `sync_configuration.rs`, `sync_conflicts.rs`, `sync_context.rs`, `sync_identity_repair.rs`, `sync_ledger.rs`, `sync_manifests.rs`, `sync_projection.rs`, `sync_queue.rs`, `sync_recovery.rs`, `sync_snapshot.rs`, `sync_song_aliases.rs`, plus `remote_resources.rs` and `resource_retention.rs`. Nested implementation modules already exist under ledger, snapshot and projection. Their methods are `SqliteDatabase` capability implementations, called through Core ports; tests are registered from `sqlite/tests/mod.rs` and include dedicated sync test modules. Some tests reach internal helpers through parent-relative paths. Any aggregation must preserve the public/internal `sync` facade and audit Rust module-parent paths, nested `#[path]`, visibility, `include!` paths and transaction bodies. Empty remote polls deliberately use a reader; non-empty applies use the writer. Publication, checkpoint recovery, snapshot and projection operations retain their existing atomic transaction and wake-up boundaries.
- `echo-sync` owns LAN protocol/client/server, discovery, pairing and resource transport; it adapts to Core ports and does not own SQLite. `echo-desktop` owns platform/security adapters. Tauri owns session runtime, IPC DTO conversion and composition. React `features/sync/lanSyncAdapter.ts` owns typed IPC access; `useAppShell` owns cross-feature catalog refresh. No frontend move is warranted by the current ownership evidence.
- Runtime contracts are in `apps/desktop/src-tauri/src/sync_runtime.rs`. `SyncProvisioner` contains provisioning/lifecycle methods, but `SyncCyclePort: SyncProvisioner` currently combines them; `SyncRuntime` stores only the cycle port and lifecycle methods are reached through inheritance. Runtime lifecycle consumers are in `sync_runtime/control.rs`, `pairing.rs`, and `session.rs`; the cycle loop consumes cycle methods in `sync_runtime.rs` and `sync_runtime/sync_loop.rs`. `NativeSyncProvisioner` implements both and production composition must supply the same concrete adapter to the respective collaborator slots. Scripted implementations and runtime tests live under `sync_runtime/tests/`.
- `ProvisionedPeer` currently includes `LanClient`, but runtime peer startup uses binding/address; transport calls are made in `sync_provisioner/peer_sync.rs`. Keep transport client ownership in the adapter and remove it from runtime-facing data if the full consumer/test audit confirms no runtime need. This must not alter peer identity validation, endpoint handling, or session startup.
- The `NativeSyncProvisioner` constructor is side-effect-free. Field-level lifecycle and sharing are recorded in `provisioner-state-ownership.md`; the shared binding-scoped `FileResourceStore`, operation gate, wake channel and caches must not be separated without an independently justified owner/test boundary.
