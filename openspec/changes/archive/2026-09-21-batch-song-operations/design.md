## Context

See `proposal.md` for the motivation and behavior contract. 当前桌面端已经有共享的 `SongList`/`SongRow`、虚拟列表、`SongMenu`、`AddToPlaylistDialog`、收藏广播与 `delete_song`/`undo_delete` 命令。资料库分页会把已加载歌曲保留在当前页模型中，歌单视图则一次加载成员；两者都需要共享稳定 Song UUID 的选择模型。当前根目录只读状态由工作区传入，Core 仍不能依赖 React、Tauri 或播放器。

## Goals / Non-Goals

**Goals:**

- 在共享歌曲列表上提供可访问的 UUID 选择模型，并同时支持选择控件、全选、右键和键盘菜单快捷键。
- 让资料库视图和歌单视图复用同一套选择与批量结果语义，保持窗口化渲染不影响已选状态。
- 优先复用现有单曲 command 和刷新/广播机制，在桌面侧串行编排并聚合结果。
- 将批量删除的多个 operation id 绑定为一次用户可见的 10 秒撤回入口，并对部分成功明确反馈。
- 保持 Core 与 UI 的依赖方向、IPC 类型集中管理、错误可观测和现有单曲入口兼容。

**Non-Goals:**

- 不实现矩形框选、拖拽多选、跨视图/跨会话选择或批量元数据编辑。
- 不把选择状态写入 SQLite、同步对象或播放会话。
- 不在本次变更中新增通用 Core 批量领域 API；只有当既有单曲命令无法满足明确的整批撤回/一致性要求时才升级边界。

## Decisions

### 1. 以选择控制器保存 UUID 集合，列表组件只负责呈现

在桌面 UI 增加小型 `useSongSelection` 状态抽象，由工作区按当前视图身份、搜索词、排序、根目录和歌单 id 建立 selection key。它保存 `ReadonlySet<SongId>`，提供 toggle、selectAllLoaded、clear 和 selection summary；`SongList`/`SongRow` 只接收受控的 selected 值和回调。

这样可以把虚拟行的生命周期与选择生命周期分离：行离开窗口后选择仍存在，重新渲染时由 UUID 恢复。查询上下文变化时由 key effect 清空，避免旧搜索结果中的隐藏歌曲被新视图误操作。替代方案是把选择状态放进每行或依赖 DOM 勾选状态，但会在窗口化滚动和分页加载时丢失状态。

正常模式保持原型的紧凑列表，不渲染任何选择圈或批量状态信息。排序控件后增加一个进入/退出多选按钮；只有进入多选模式后，列表才在序号左侧增加独立的选择列，行选择圈不占用序号位置，表头选择圈只覆盖当前已加载集合。多选行使用独立的 `bulk-selected` 视觉/ARIA 语义，不复用当前播放行的 `selected` 类；已选数量只在右键批量菜单头部显示。

### 2. 统一单曲菜单与批量菜单的数据驱动动作

保留现有菜单定位、浮层栈、焦点陷阱和 Escape/外部点击行为，将菜单动作抽象为单曲或批量两种上下文的 action descriptors。多选状态下右键未选中行先把该行设为唯一选中项；右键已选中行保持完整选集。列表行的 `contextmenu` 和键盘菜单键/`Shift+F10` 都进入同一批量菜单路径。

批量菜单仅展示可以对集合解释的动作：收藏/取消收藏、加入歌单、下一首播放、加入播放队列、从当前歌单移除（歌单视图）和删除（可写根目录）。详情、显示目录和单曲播放等必须依赖一个 SongView 的动作隐藏或禁用。右键和键盘菜单调用同一批量 action runner，避免不同入口出现不同的权限和错误规则；多选模式不显示顶部批量工具条。

### 3. 桌面侧串行编排单曲 command，使用结构化批量结果

新增 UI 侧的 batch runner/结果类型，按稳定选择顺序串行执行既有 command：

- `set_favorite`：对每首目标提交同一个目标状态，发布每个已提交的权威 `SongView`，最后统一 reset/recount；失败项记录错误。
- `add_to_playlists`：扩展 `AddToPlaylistDialog` 接收一个或多个 song id，歌单选择确认后逐曲调用现有 command；重复成员作为已处理/跳过，其他错误进入结果明细。
- `remove_playlist_song`：按当前歌单显示顺序逐曲调用，成功后刷新成员和导航计数。
- `queue_command`：加入队列按显示顺序执行；“下一首播放”按选集逆序提交，保持最终队列中的用户可见顺序。
- `delete_song`：按显示顺序串行删除，收集每个成功返回的 operation id；单项错误不会静默丢失，也不会把未执行项标成成功。

串行而不是并发的理由是复用现有播放器协调、SQLite 提交和错误边界，避免多个删除同时争用当前播放文件、避免 `playNext` 插入顺序不确定，并使结果顺序稳定。替代方案是在 Core 增加批量事务/command，理论上能减少 IPC 往返，但会扩大跨层契约、播放器协调和迁移审查范围；本 change 先验证体验，保留后续下沉批量用例的切入点。

### 4. 批量删除使用操作 id 集合实现一个撤回入口

批量删除成功项的 operation id 存在内存中的撤回闭包中，显示一个带 10 秒期限的汇总 toast。用户点击撤回后按原批次的安全顺序逐个调用 `undo_delete`，成功恢复项刷新列表和计数；任一撤回失败都显示错误，不伪造整批恢复成功。toast 只提供一个批次级入口，避免用户面对多个单曲撤回按钮。

部分成功时 toast/结果面板明确显示成功、跳过和失败数量；成功项仍提供撤回，失败项保留原因。应用重启后不承诺恢复这段内存撤回入口，继续遵循现有单曲删除的短时撤回语义。

### 5. 不新增 IPC command，保持边界兼容

第一版不修改 `BridgeCommandArguments`、`IpcCommandResultMap` 或 Rust command 注册表；批量结果是 UI 编排层的内部类型，单曲 command 的现有参数/返回值/错误码保持兼容。若实现验证发现逐曲调用无法满足撤回或性能验收，必须另开明确的 IPC/Core 设计，不能在本 change 中通过动态 map 或未类型化 command 绕过桥接边界。

### 6. 按现有刷新和广播边界收敛状态

收藏沿用 optimistic count + 权威 `SongView` 广播 + 失败回滚；批量 runner 在全部单项完成后再执行一次权威 reset/recount，避免中间页不断抖动。加入/移除歌单刷新当前成员和导航列表；删除刷新所有受影响视图和计数。批量操作完成后退出多选模式并清空 selection；部分失败仍保留错误结果反馈，但不保留已经提交项的隐式选中状态。

## Risks / Trade-offs

- [Risk] 大选集串行调用会增加完成时间和 IPC 往返 → 限制为当前已加载集合，显示进行中状态，先用测试覆盖结果聚合；后续若有证据再下沉 Core 批量接口。
- [Risk] 多个删除 operation 的撤回可能出现部分恢复 → 每个 undo 结果独立记录，toast 明确“恢复 X/Y”，不宣称全成功；单个失败保留可诊断错误。
- [Risk] 右键与现有行点击/播放事件互相干扰 → 在行级 `contextmenu` 阻止默认菜单并仅更新 selection，不触发播放；选择控件继续阻止事件冒泡。
- [Risk] 虚拟列表全选容易被误解为全库全选 → 全选按钮文案和计数明确“已加载”，规格只保证已加载页；实现测试覆盖滚动前后 UUID 保持。
- [Risk] 单曲菜单和批量菜单动作规则漂移 → 共享动作描述和 eligibility 函数，分别测试单曲与批量的只读、不可用和错误路径。
- [Risk] UI 文件过大或职责混杂 → 选择 hook、批量 runner、批量结果展示和菜单动作描述拆成职责匹配的小模块，遵守 React 组件可测试与文件规模规范。

## Migration Plan

1. 先添加选择模型、批量结果类型和共享菜单/runner 测试，再接入 `SongList`、`LibraryWorkspace` 和 `PlaylistsView`。
2. 扩展歌单选择器以接受单曲或多曲 id，保持现有单曲调用的兼容适配。
3. 添加多选入口、选择列和右键/键盘交互，执行 TypeScript、React 测试、格式与静态检查。
4. 不需要数据库迁移或用户数据迁移；旧的单曲 command 和已有持久化数据继续有效。
5. 若回滚，只移除多选入口和批量 runner；单曲菜单、收藏、歌单和删除 command 不变。
