# playlist-management Delta

## ADDED Requirements

### Requirement: 歌单与成员以音乐库持久结果反馈

歌单创建、重命名、删除、封面修改及成员添加/移除 MUST 在音乐库可靠提交定义、关联、资源或类型化墓碑之后更新已保存状态；SQLite 投影可在后台滞后，不得让滞后读模型覆盖已保存状态。目录已保存而投影失败 MUST 保留稳定操作身份并显示已保存待更新，不得当成可直接重新创建的未保存失败。未提交失败维持原界面；已提交待投影保留真实保存状态。歌单与成员连续编辑 MUST 从已验证的权威状态读取前一条已保存变更。批量操作 MUST 沿现有单项粒度报告，成员去重、追加顺序、时间及删除不影响音乐文件的语义保持。

从桌面服务命令开始处理到返回已保存结果，创建歌单、加入歌单和移出歌单在 1,000 与 10,000 首资料库的 Release 验收场景中 P95 MUST 小于 50 ms；测量 MUST 包含计划、可靠目录提交、必要的前台投影追赶和响应构建，不包含后台 SQLite 投影完成时间。完整桌面点击至反馈延迟仍须单独验收。

#### Scenario: 创建空歌单后重装
- **WHEN** 用户成功创建没有任何成员的歌单，随后清除应用数据并重新选择原音乐库
- **THEN** 原歌单 UUID、名称和已知创建时间被恢复，不依赖成员记录推断其存在

#### Scenario: 多成员提交被中断
- **WHEN** 成员操作涉及多个记录，进程在目录已提交但数据库尚未投影时崩溃
- **THEN** 重启按原成员 UUID 和追加顺序恢复已提交项，重复请求不产生第二成员或重写原加入时间

#### Scenario: 保存与显示更新分离
- **WHEN** 歌单定义或成员变更已提交到音乐库而 SQLite 投影仍在运行或暂时失败
- **THEN** 界面明确显示变更已保存，可按需说明等待更新，保留同操作身份，不将用户输入清空并诱导创建另一个歌单；后台投影完成不会重复执行变更

#### Scenario: SQLite 落后时连续编辑歌单
- **WHEN** 一条歌单创建或成员变更已可靠提交到音乐库而 SQLite 尚未追平，用户立即执行下一条歌单操作
- **THEN** 新操作基于前一条已保存状态规划，保留成员唯一性、追加顺序和加入时间，前台不等待 SQLite 全量追平

#### Scenario: 歌单命令低延迟验收
- **WHEN** 在 1,000 与 10,000 首资料库上按 Release 验收口径测量创建、加入和移出歌单命令
- **THEN** 每类命令从服务处理开始至已保存响应的 P95 小于 50 ms，计入可靠目录提交和必要的前台追赶，单独报告目录提交与后台 SQLite 投影延迟

#### Scenario: 删除与取消喜欢不复活
- **WHEN** 用户成功删除歌单/成员或取消喜欢，之后数据库被重建
- **THEN** 对应删除或 false 状态从音乐库恢复，旧记录不能使其重新出现，其他歌单和歌曲保持原有语义
