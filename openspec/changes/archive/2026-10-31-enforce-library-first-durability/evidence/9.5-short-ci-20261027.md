## 三、并发污染：首次治理门 exit 1 的真实原因

首次 `pnpm verify:governance` 以 `GOV_EXIT=1` 结束，失败两行：

```
FAIL ci-platform-matrix/missing-linux-entry: positive control failed: gate exits 1 on the untouched tree
FAIL 1.5: 'cargo test --workspace --all-features' exited 101
```

底层是同一个 panic：

```
sync_runtime::tests::host_resources::cases::http_peer_tag_update_is_published_by_the_host_loop_without_manual_sync
panicked at apps/desktop/src-tauri/src/sync_runtime/tests/host_resources.rs:237:
accepted HTTP mutation was not published by the host loop
```

**判定：并发污染，不是代码回归。** 但归因要分开说，证据强度不同：

**确定的部分（直接实测）：**

1. 同一门运行内，echo-app 套件早先已 `133 passed / 0 failed / 2 ignored`（`/tmp/95-governance.log:201`）。
2. 该测试单独跑通过（`cargo test -p echo-app -- --exact <name>`，11.62s，exit 0）。
3. 隔离复跑 `task-1.5.mjs`（无并发 cargo）**exit 0**，其内部正是全量
   `cargo test --workspace --all-features`。
4. **整门复跑（无并发 cargo）`GOV_EXIT=0`，注入 33/33**，同一棵树、同一工作区状态。
5. `host_resources.rs:237` 的 `Duration::from_secs(5)` 硬超时来自 `main` 的 `99e0234`；
   本分支对该文件只**新增**一个歌单用例与 `EnsureControlPlane` 调用，未改该测试的等待逻辑。

**不完全确定的部分（如实记录）：**

首次门运行期间我确实启动过一个后台 shell（`bv4p5fzto`，06:12:45 起，120s 超时后被杀，
输出仅 `head: illegal line count -- 0` / `[killed]`）。该命令本身不跑 cargo，
但它内含的 `rg` 扫描与 `node -e` 仍在与门的 `task-1.5.mjs` 争 CPU/IO。
`host_resources.rs:237` 等的是一个**5 秒**的墙钟期限，属对机器负载敏感的断言。
因此最可能的原因是门内全量 workspace 测试与这台机器上的其他活动共同造成的负载，
而**不是**某一次具体的并行 cargo —— 我先前把原因径直归为"并行 `cargo test -p echo-app`"，
这一步超出了现有证据。可确定的是：**同一棵树、同一工作区状态、无额外负载时整门 exit 0**，
失败在该条件下不可复现。

由此得到的操作结论（已写入后续流程）：治理门必须**独占**运行，
期间不启动任何其他消耗 CPU/IO 的命令，包括只读的 `rg`/`node` 扫描。
