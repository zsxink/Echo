# 9.4 小规模代表场景的功能正确性、持久化顺序与可观察 IO 成本（2026-10-27）

## 结论

扫描、受控批量导入与同步收敛三类场景在小规模代表数据上验证通过，且三条性质均有具名断言：

1. **唯一权威先落盘**：每次业务提交都在目录侧产生一次 authority commit，SQLite 只是其后的投影。
2. **持久化顺序**：入站同步先落 catalog 对象再取媒体；出站上传在主机 ACK 前不重复声明资源；
   每轮合并先拉主机再上传本地。
3. **IO 成本可观察且不以后置落盘换性能**：扫描 3 首新歌 = 3 次 commit（每次 1 record + 1 resource），
   无变化重扫 **0 次新增 commit**；2 首导入 = 4 次 commit（每首"身份预留 + 歌曲 after-image"两次），
   只有歌曲 commit 携带 portable record 与媒体资源。

本任务**不**设大库吞吐门槛，也**不**设"约 1 秒发现/取消"性能门槛 —— 那属于后续独立验收。

## 一、扫描（scan）

代表场景：3 首新歌写入临时库后一次扫描；随后对同一目录无变化重扫。

| 断言 | 用例 | 位置 |
| --- | --- | --- |
| 3 首歌 = 3 次 authority commit，每次恰好 1 record + 1 resource | `library_durability_small_scan_commits_one_record_and_resource_per_song` | `application/scan/tests_durability.rs:59` |
| 无变化重扫 commit 数仍为 3（**新增 0 次 IO**），身份分配稳定 | 同上 `:86-104` | 同上 |
| 目录重放先于本地投影；投影拒绝时返回 `LibrarySavedPending` 且本地投影闭包从未执行 | `library_durability_song_commit_runs_ordered_replay_before_site_projection` | 同上 |
| 扫描后清空投影库，仍从目录恢复相同 Song UUID / added_at / 标签 | `sqlite_scan_after_projection_wipe_rebuilds_the_saved_identity` | 5.2 已验收用例 |
| 同字节重写触发重解析不产生新同步候选、对象 revision 不变 | `sqlite_scan_reparsing_unchanged_song_does_not_create_a_candidate` | 5.2 已验收用例 |

**持久化顺序**：`persist_parsed_index` → 目录 commit（record + resource）→ 投影。IO 成本按"新歌数"
线性，不随库总量增长；无变化重扫为纯读，不产生任何目录提交，符合"不以延迟唯一权威落盘换性能"。

## 二、受控批量导入（controlled batch import）

代表场景：同一批次两个源文件（不同内容、同歌手不同标题），全部成功。

| 断言 | 用例 | 位置 |
| --- | --- | --- |
| 2 首导入 = 4 次 commit（每首"身份预留 + 歌曲 after-image"）；record 总数 2、resource 总数 2 | `library_durability_small_import_records_reservation_and_song_commit_per_success` | `application/import/tests/execution.rs:38` |
| 单条输入失败不回滚已提交输入 | `single_input_failure_does_not_rollback_committed_inputs` | 同上 |
| 同批次重复内容只产生 1 个 record | `duplicate_content_within_a_batch_creates_one_record` | 同上 |
| 导入的歌曲 record 携带非零 `added_at` | `imported_song_record_carries_a_non_zero_added_at` | 同上 |

**持久化顺序**：资源校验安全发布 → 目录提交（先预留身份，再写歌曲 after-image）→ SQLite 投影。
身份预留在目录侧可恢复，重试不重新分配 UUID；界面只报一个导入结果。**IO 成本**为每成功导入 2 次
commit，与 5.1 的"预留 claim / 提交 Song"两段操作身份设计一致。

## 三、同步收敛（sync convergence）

代表场景：`LanMergeFixture`（真实 LAN 主机 + 单从，临时目录 + 独立 SQLite）执行合并周期。
本任务允许较长同步等待，故不设时延门槛，只验证功能正确性与顺序。

| 性质 | 用例 | 位置 |
| --- | --- | --- |
| 合并先拉主机再上传本地，本地歌曲字节保持不变，两侧收敛到 2 首 | `native_merge_pulls_host_before_uploading_and_preserves_local_song` | `merge_cycle.rs:10` |
| 从端在主机 ACK 前不重复声明资源（`prepare` 只调一次） | `native_upload_prepares_a_resource_once_until_the_host_acks_it` | `merge_cycle.rs:589` |
| 入站 catalog 对象先落地，媒体随后按持久 manifest 补齐 | `native_enrollment_persists_host_manifests_before_downloading_audio`、`native_incremental_applies_objects_before_audio_arrives` | `merge_cycle.rs:406` / `:457` |
| 已收敛周期只读一页主机提交，不按阶段重复拉取 | `an_idle_cycle_reaches_the_host_exactly_once` | `merge_cycle.rs:232` |
| 从端周期发送目录中已保存的原歌单（冻结 mutation 的 `origin_seq` 与前驱链） | `library_durability_replica_cycle_sends_original_saved_playlist` | `merge_cycle.rs:127` |
| 已确认远端墓碑压过本地删除意图 | `confirmed_remote_tombstone_supersedes_local_delete_intent` | `merge_cycle.rs:518` |
| 快照冻结后增量恰好收敛一次 | `enrollment_snapshot_is_frozen_and_incremental_pull_after_h_converges_once` | `tests.rs` |
| 主机在报告就绪前把对端上传音频发布进自己的库 | `host_publishes_peer_uploaded_audio_into_its_library_before_reporting_ready` | `tests.rs` |
| 慢目录应用期间传输保持可响应 | `blocking_apply::native_pull_keeps_transport_responsive_during_slow_directory_apply` | `blocking_apply.rs:63` |
| 缺失音频维护不产生新传输或新 mutation | `maintenance_restores_completed_missing_audio_without_new_transfers_or_mutations` | `missing_publications.rs` |

**持久化顺序**：`enroll_peer_snapshot` → `replica_checkpoint` → `recover_saved_sync_state(Replica)` →
循环 {拉取 → 发布远端资源 → 上传本地资源 → 增量周期 → 再发布 → 直到 pending 为空或
`SyncPredecessorPending`} → `reconcile_remote_delete_isolation`。出站资源在主机 ACK 前只声明一次，
避免了"未 ACK 就重复上传"的 IO 放大。

**可观察 IO 成本**（非时延）：一轮已收敛周期的成本是**一页**主机提交读取（
`an_idle_cycle_reaches_the_host_exactly_once`），出站资源声明为**一次** `prepare`
（`native_upload_prepares_a_resource_once_until_the_host_acks_it`）；两者都由计数的 port 适配器
（`CountingLedger` / `CountingResources` / `ObservePullBeforePush`）实测，不是推断。

## 未覆盖项（如实记录）

- 本轮**未**测量大库吞吐或 `discover`/`cancel` 的秒级延迟 —— 按任务口径明确不设该门槛；
  512+ 规模用例仍为 `#[ignore]`，归后续独立验收。
- 同步验证为**进程内** LAN fixture（真实 HTTP 传输 + 临时目录 + 独立 SQLite），不含三平台原生
  文件系统语义；原生断电/权限/卷断开属 9.3。
- 主机 + 两从的综合场景属 9.1，不在本任务；本任务只覆盖主机 + 单从的收敛。
- 时间只记录到测试框架输出的整轮耗时，未做单场景分项计时；本任务不以此为门槛。
