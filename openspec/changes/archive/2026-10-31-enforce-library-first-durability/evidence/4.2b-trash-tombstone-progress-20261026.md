# 4.2b progress: directory-first trash tombstone

Date: 2026-10-26

## Change made

Expired delete finalization now commits the shared typed Song tombstone and the `Finalized` local delete intent together in one deterministic `LibraryBatch`. The SQLite transaction that deletes the catalog row, playlist relationships, and operation claims runs only after that directory commit succeeds.

The finalization batch ID is derived from the delete operation and a versioned stage name. Re-entry reads and reuses the saved batch, including its exact tombstone after-image, so the tombstone revision/body is not recomputed after a failed SQLite transaction. The database transaction remains atomic for catalog deletion, journal terminalization, and claim release.

## Continuation failure guard

Candidate-root preparation no longer converts a failed object-record continuation into a plain scan. A continuation or replica-enrollment query error now aborts preparation before scanning; only an unsupported newer manifest remains a browseable read-only degraded case. The focused regression injects a projection transaction failure and verifies that no scan generation starts and no new song identity is minted.

## Ordered continuation projection

Production root switching and `RestoreLibrary` now use `LibraryProjectionPort`. For manifest v3, continuation reads the verified replay, projects only uncovered legacy snapshots first, and then applies real commits in directory order. Snapshot selection is typed by object identity and compares `(HLC, revision)` with tombstones winning ties. SQLite's legacy projector only materializes rows and retains unresolved references; it does not write directory records, synthesize commits, advance the commit watermark, or enqueue sync candidates. `commit_song` also catches the projection up from the saved replay before running its call-site-local index and journal transaction.

Echo continues to read external music tags and does not write tags back to source media files.

## Controlled failure-order coverage and retry repair

The SQLite-backed `RefusingAuthority` tests now exercise directory refusal at four delete lifecycle boundaries:

- `delete_directory_refusal_does_not_change_user_projection_or_directory_replay` proves a refused delete intent leaves catalog/user tables and the replay unchanged.
- `undo_directory_refusal_keeps_hidden_song_and_staged_media_for_retry` proves undo does not move media or expose the song before the cancellation commit, then converges on retry with the same operation.
- `trash_directory_refusal_keeps_applied_receipt_and_retries_same_tombstone` proves an OS-trash receipt remains durable in the local journal while SQLite keeps the song; retry commits the tombstone without calling system trash a second time.
- `recovery_directory_refusal_keeps_pending_delete_until_cancel_can_commit` exposed and fixed a retry hole: recovery could persist every item as `Restored`, fail to commit the directory cancellation, and then SQLite excluded those terminal rows even though the song remained `PendingDelete`. `incomplete_operation_items` now re-queues restored delete items while their song is still pending deletion. The refusal/retry regression passes.
