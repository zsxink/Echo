# 9.6 DB-first / DB-only 残留复核与边界审查（2026-10-27）

## 结论

以 CodeGraph 调用链 + 引用搜索对四个边界（事务、迁移、身份、API/权限）独立复核后：

- **生产可达的 DB-first 用户业务事实写入只剩 1 处**：`resolve_host_sync_conflict`
  （`crates/echo-core/src/infrastructure/sqlite/sync/sync_conflicts.rs:139-189`）。
  它**未经目录提交**就写 `songs`/`playlists`/`song_overrides` 业务值、铸造新上传候选并改写冲突终态。
- **1 处已由规划明确保留**：`ensure_replica_sync_baseline` / `ensure_host_sync_baseline`
  （`sync/sync_baseline.rs`）把 SQLite 当前状态铸成 outbox 基线，无目录提交；
  `tasks.md:92` 已记录"其余发射点与 baseline 重发保持无条件铸造"为有意行为。
- **1 处非用户事实旁路**：`sync_provisioner/enrollment.rs:43-113` 用裸 `std::fs` 写
  `echo/manifest.json` 与 `echo/tmp/.echo-ownership-marker`，绕过 Core 的 `write_manifest`
  （`control_plane.rs:335-348`：格式兼容校验 + 临时文件/rename/父目录 fsync）。
  不写用户业务值，但属"权威目录文件由 Core 之外写入"。
- 其余全部干净：迁移、身份派生、IPC 写入口、旧 materializer 清理均符合 LD-01/10。

上述第 1 项与 `design.md:282`（"继续使用既有同步冲突入口"）并不矛盾——该行只规定**路由**
（禁止把目录复制当版本合并，冲突仍走既有 UI），并未豁免该入口的目录优先提交义务。
但把冲突记录本身迁入目录超出本 change 已规划范围，属需上报的范围扩张，故本轮只出证据、不改实现（见末节）。

## 一、事务边界

| 类别 | 判定 | 依据 |
| --- | --- | --- |

| `sync/sync_apply.rs:377,382` | 合规 | 写确认态，但同事务由 `commit_projection`(:146) 收口，目录先行 |

## 二、迁移边界

**否。** `connection.rs:102-161` 的 `apply_migrations`/`apply_migration_set` 只建表/加列并写
`schema_migrations`（BLAKE3 校验和不可变，:154-161 含 v19 pin 与 v20 例外），每版本独立事务；
用户值只在目录 replay 之后经 `durability_projection::project_commits`
（`durability_projection.rs:41-99`）写入。投影重建的候选库也先 `apply_migrations` 再
`project_commits`，且 `replace_active` 比对协议表与 `sync_mutations`/`sync_outbox` 计数后才切换
（`projection_rebuild.rs:101-110,231-289`）。

## 三、身份边界

**未发现新的"以 SQLite id/HLC 为权威"路径。** 生产写路径的对象/操作身份均来自目录：
`library_commit.rs:14-55` 的 `OperationId::from_uuid(operation)`、`commit.rs:161-174`、
`StateKey::storage_id()`（`state.rs:206-215`，BLAKE3 域分隔 + 规范化 JSON）。

唯一在 SQLite 内派生新身份/时钟的仍是 `sync_conflicts.rs:175-180`
（`current_outbox_revision` 自增、`device_state` 取 device、`advance_object_hlc` 推 HLC）——即上文唯一违规项。

## 四、API / 权限边界

- 用户变更 IPC（`apps/desktop/src-tauri/src/commands.rs:342-428`）全部经
  `services.*` → `DurableLibraryEdits` / `plan_library_change`（`local_library_edit.rs:228-288`）。
- `resolve_sync_conflict`（`sync_commands.rs:118-133`）是唯一把 `Arc<SqliteDatabase>` 直接暴露给
  IPC 的写入口；它仍调用 `require_host`（`sync_conflicts.rs:16-32`）校验 binding/epoch/active-root，
  **未绕过 authority**，但绕过了 `commit_then_project`（=上文唯一违规项）。
- 非用户事实旁路：`sync_provisioner/enrollment.rs:43-62,77-113`（生产可达路径
  `provisioner_trait.rs:197` → `complete_peer_pairing`）。仅在新库/未创建时 `create_new` + `sync_all`，
  不覆盖既有 manifest；但缺少父目录 fsync 与格式兼容校验。
- 只读面：`play_temporary_file`（`commands.rs:780-790`）接受 WebView 传入绝对路径，
  actor 只拒绝含 `://`（`player/actor/mod.rs:907-934`）——属播放面，非资料库写入，不在 LD-01 范围。

## 五、旧 materializer / fake / 导出清理

`rg -n 'write_record_guarded|materialize_playlist|record_play_stats|record_playback' crates apps/desktop/src-tauri`
在 6.6 已验收（仅剩解释性注释）；本轮复核未新增生产定义或调用。`with_tx` 无生产调用者；
`continuation.rs` 的 legacy `project()` 在 4.2b 后无生产可达路径。无 `DbFirst` 符号。

## 六、未闭合项与上报范围

`resolve_host_sync_conflict` 的修正**不是**把一次写改成 `commit_then_project` 即可：
`sync_conflicts` 行本身由同步应用在 SQLite 中产生，目录侧 `StateKind::Conflict`
（`durability.rs:158`）是**从 SQLite 导出**的，`resolved_at` 亦只存于 SQLite。
因此要让该入口满足 LD-01，需要把冲突记录及其终态一并迁入目录生命周期（新的 state 写入点 +
目录提交 + 重建时不再从 SQLite 反向导出），并补齐 `LocalLibraryEditPort` 的覆盖层写入口。
这超出本 change 已规划范围（`design.md:282` 只要求保留该 UI 入口），按 skill 约束上报而非静默吞掉。

`ensure_*_sync_baseline` 的无条件铸造已由 `tasks.md:92` 记录为有意行为，无需改动；
但主规格 LD-01 的文字（"所有来源…MUST 先可靠提交到本地音乐库"）未写明该豁免，
同步 delta 时需决定是补一句规格豁免还是保留为已知偏差。
