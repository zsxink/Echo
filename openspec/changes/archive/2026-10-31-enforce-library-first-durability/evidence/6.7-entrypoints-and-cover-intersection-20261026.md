## 1. 各入口持久化/错误说明已更新

`docs/library-durability-protocol.md` 新增 `## 各入口持久化与错误语义` 表，覆盖
导入、扫描/外部标签/移动、喜欢、歌单（创建/改名/删除/成员）、歌单与艺术家封面、
播放统计、删除/撤销/回收、启动续跑、LAN 入站快照/增量、来源 ACK/主机确认共
11 类入口，逐条写明"目录先提交的事实"与"失败语义"。

错误语义只在 Core 分类：`Error::code()` 产出
`library_saved_pending_recovery` / `library_saved_pending_projection`，IPC
（`crates/echo-desktop/src/ipc/error.rs:55-78`）映射为
`library.savedPendingRecovery` / `library.savedPendingProjection` 并附带原
`operationId`；`ErrorPolicy::retryable`（同文件 `:109-129`）把两类都标为非
"新命令可重试"，即必须用同一 operation 恢复而不是重新提交。共享/同步正文不含
播放会话标识这一条同时写在 `## Cross-cutting write contract`
（`evidence/entrypoints.md`）与新表格下方。

## 2. 与歌单 UI change 的封面字段交汇已记录

`docs/library-durability-protocol.md` 新增 `### 与歌单封面 UI change 的字段交汇`。
交汇字段只有一个：`PlaylistView.coverKey`。

- 对方规格：`openspec/changes/align-immersive-player-and-playlist-directory/specs/playlist-management/spec.md:23-37`
  （预览、保存后卡片与导航同步、重命名不丢封面、失败保留名称与已有封面、不得用
  按名称索引的 `localStorage` 模拟替代稳定歌单身份）。
- 本 change 提供：`PortableRecord::Playlist.cover_asset`（内容寻址原件引用）→
  读模型派生 `coverKey`；清空应用缓存后由 `echo/assets/<blake3>` 重建同一 key；
  历史仅 cache key 的封面显式报"历史封面无可恢复原件"，不得显示为已保存封面。
- 前端实际使用点：`apps/desktop/src/features/playlists/PlaylistsView.tsx:59-77,723-725`、
  `PlaylistNameDialog.tsx:32-48,248`、`AddToPlaylistDialog.tsx:222-226`
  （`coverKey` 走 `bridge.assetUrl`，`hasCustomCover` 决定是否显示清空入口）。

## 3. 无平台绕过 Core 的用户变更

复核范围：`apps/desktop/src-tauri/src`（Tauri 壳）与 `crates/echo-desktop/src`
（平台适配层）。

| 检查 | 命令 | 结果 |
| --- | --- | --- |
| Tauri 壳是否存在直接 SQL 写 | `grep -rn "with_tx\|writer\.run\|execute_batch\|INSERT INTO\|UPDATE \|DELETE FROM" apps/desktop/src-tauri/src`（排除 tests） | **0 命中** |
| 用户变更命令是否只转发到 AppServices | `grep -n "pub fn set_artist_cover\|pub fn set_favorite\|pub fn create_playlist\|pub fn rename_playlist\|pub fn set_playlist_cover\|pub fn delete_playlist\|pub fn add_to_playlists\|pub fn remove_playlist_song" apps/desktop/src-tauri/src/commands.rs` | 8 个命令全部形如 `services.<method>(...).map_err(IpcErrorDto::from)`（`:216,303,315,327,339,352,360,376`） |
| 桌面服务是否只经协调器 | `crates/echo-desktop/src/runtime/services/playlists.rs:8-83`、`favorites.rs:11-14`、`catalog.rs:171-184` | 全部经 `library_edits() -> DurableLibraryEdits` 或 `application::artist_cover::set_artist_cover` 转发；无本地写库分支 |
| 桌面层直接访问目录适配器的位置 | `grep -rn "durability()" crates/echo-desktop/src apps/desktop/src-tauri/src`（排除 tests） | 仅 2 处：`runtime/services/recovery.rs:44`（只读状态诊断）与 `runtime/player/recorder.rs:109`（目录事件证明 + 投影追赶），都不是绕过协调器的用户变更 |
| 架构门 | `cargo test -p echo-core --test arch` | 8/8 通过，含 `library_durability_ports_do_not_grow_the_legacy_control_surface` |
| 旧 DB-first 入口 | 6.6 已复核：`record_playback`/`materialize_playlist`/`record_play_stats` 无生产定义/调用 | 保持 |

结论：用户可发起的 8 个变更命令（喜欢、歌单 4 个、成员 2 个、艺术家封面）加上
导入、扫描、播放统计、删除/回收，全部经 Core 的 `plan_library_change` 目录先提交
路径；平台层没有自己的写库或写目录路径。
