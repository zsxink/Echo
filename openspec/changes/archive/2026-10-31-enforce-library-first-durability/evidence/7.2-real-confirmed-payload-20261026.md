# 7.2 真实 confirmed payload 与误确认语义验证矩阵（2026-10-26）

## 结论

目录信封里的 `sync` 块由"声明"降级为"待证主张"：只有 `sync_commits` 里
同 binding（`library_id`/`authority_id`/`epoch`）、同 `commit_seq`、摘要自校验
通过、且载荷与磁盘值一致的账本事件，才算确认。其余情况保留原件字节、
继续投影本地值（目录仍是唯一真相），但行上持续报告
`UnverifiedConfirmationMetadata`，且**不**为未证值落 `sync_object_versions`
confirmed baseline。

新增矩阵 `crates/echo-core/src/infrastructure/sqlite/durability_projection/tests/stale_sync.rs`
5/5 通过；`cargo test -p echo-core sync` 209/0。

## 发现的真实缺陷：旧 sync metadata 附到新值被当成已确认

`PortableRecordEnvelope` 的 v2 `sync: Option<PortableSyncMetadata>` 是随记录一起
落盘的结构化字段。本地编辑替换值的路径（`control_plane.rs:357-386`
`write_record`）在非持久批内会**原样携带旧 `sync` 块**，因此"新值 + 旧
`object_version`"是一种完全合法可持久化的信封。

而 `durability_projection/retained.rs::retry` 在重放时用
`reason(c, root, &key, unresolved)` **覆盖**该行的 `unresolved_reason`，
`unresolved` 只来自 `dependencies::unresolved(...)`（父记录是否可得），
完全不看 `sync` 块。后果有两个方向：

- 任何读路径若把 `sync.object_version` 当作"已确认到第 N 版"的证据，
  就会为新值建立**虚假 confirmed baseline**（正是 spec scenario
  「v2 本地覆盖值混有旧确认元数据」禁止的行为）；
- 反过来，若想在上游把这种信封标记为"待核对"，`retry` 会把标记清掉，
  因为它是从依赖重新算的。

## 修复

**`durability_projection/confirmation.rs`（新增）**：`unproven(c, envelope)` 回答
"该声明能否被账本证明"。

1. 无 `sync` 块 → 不声明，`false`；
2. `object_version == ObjectVersion::INITIAL`（`CommitSeq::GENESIS = 0`）→
   "无主机版本"，不声明，`false`。这一点必须放行：`filesystem/durability/tests/identity.rs`
   构造的正是 genesis 元数据；
3. 以信封自带的 binding 精确查 `sync_commits(commit_seq, library_id,
   authority_id, epoch)`，查不到 → `true`（离线、迟到 ACK 之前均走这里）；
4. 用 `sync/apply::verify_remote_commit` 重算 LAN 摘要
   （`blake3("echo.lan.commit.v1\0" || version || seq || previous_digest || len || canonical_json)`），
   失败 → `true`。即"正文自称已被确认"不算证据，摘要必须自证；
5. `commit.object != envelope.record().object_key()` → `true`。序列号被
   别的对象占用时，版本是**借来的**；
6. `agrees(record, payload)` 逐字段比对账本载荷与磁盘值。只比对双方都主张
   的字段（`payload.get(key).is_none_or(...)`）：账本载荷没断言的字段不算分歧；
   歌的 `relative_path` 是主机作用域，故意不比。

**`durability_projection/retained.rs::retry`（修改）**：在排序后、投影前一次性算出
`unproven` 键集合，最终报告态改为
`unresolved.or_else(|| unproven.contains(&key).then_some(Reason::UnverifiedConfirmationMetadata))`。
两个不变量因此同时成立：

- 依赖已解决时**仍然投影**本地值——目录是真相，不能因为元数据可疑就丢失用户数据；
- 依赖已解决时**仍然报告**——否则 `retry` 会把"待核对"抹成"正常"。

字节从不在此改写：`retained_json` 在报告前后逐字节不变。

**枚举贯通**：`ProjectionUnresolvedReason::UnverifiedConfirmationMetadata`
→ `RecoveryIssueReasonDto::unverifiedConfirmationMetadata`（camelCase）
→ `apps/desktop/src/ipc/ipc-types.generated.ts` 联合类型
→ `LibraryRecoveryStatus.tsx` 文案「本地新值附有旧确认记录，等待核对」。

## 未在本项内解决

`agrees()` 只做**字段级**比对，不做逐字节规范化比对：账本载荷里多出的
字段（例如未来新增的同步专属列）不参与判定，因此"账本与磁盘在未建模字段上
不一致"不会被本机制发现。该方向的完整 wire 兼容矩阵归 7.8。
