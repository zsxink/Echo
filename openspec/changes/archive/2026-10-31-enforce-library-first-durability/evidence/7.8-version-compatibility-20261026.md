# 7.8 Version compatibility matrix (2026-10-26)

The three version axes are independent. A local manifest does not negotiate
object-envelope or LAN compatibility, and a LAN wire version does not describe
where a resource is stored in a local library.

| Surface | Current contract | Legacy and unknown input | Write behavior |
| --- | --- | --- | --- |
| Local manifest | New manifests use v3; current code recognizes v1, v2, and v3 | Invalid and future versions are incompatible; supported v1/v2 can be read | Reading does not rewrite a manifest. A v3 directory fences writers that only support v1/v2. No existing-library upgrade/backfill is implied. |
| Record document | Flat v1 and envelope v2 are distinct encodings | Supported v1/v2 decode through their respective paths; unknown envelope versions and invalid typed identities are rejected, never downgraded to flat v1 | Compatibility reads preserve historical absent fields and do not repair or rewrite published records. |
| LAN wire/capability | Mutation and commit DTOs carry protocol version 1; validation checks resource count/size, digest, MIME, and relative path | Unsupported protocol versions are rejected. Unknown optional JSON fields on DTOs are ignored by serde; unknown enum kinds are rejected | Local directory resource locations are not new wire fields. Existing `resource_refs` remain subject to v1 validation. Any future required wire semantics must use a new protocol/capability contract rather than an ignored JSON field. |

No new LAN resource field was added by this change. The directory-only owner,
declaration version, and managed location remain local recovery evidence. Thus
there is no new cross-version resource field to silently drop in this change;
the existing wire DTO behavior for unknown optional fields is explicitly
documented above.
