# 7.1 远端快照/增量目录优先验证矩阵（2026-10-26）

## 结论

快照与增量共用同一条目录优先提交尾部，`library_projection_watermarks` /
`library_applied_operations` 与可见行在同一 SQLite 事务内落库。矩阵
`crates/echo-core/src/infrastructure/sqlite/tests/sync_snapshot_apply_durability.rs`
5/5 通过，全仓回归绿。

## 发现的真实缺陷（两处）

### 缺陷 A：prepared-only 操作被当成已保存，重试永久失败

`sync/durability/commit.rs` 原用 `operation_status(...).is_some()` 判断"已保存"。
但 `filesystem/durability.rs:396-433` 对**只有 `prepared.json`、没有提交标记**的操作
返回 `Ok(Some(outcome(NotSaved)))`——`Some` 不等于已保存。因此 `"prepared"` 窗口断电后，
每次重试都走"读取已保存操作"分支，`read_operation` 找不到提交而报
`Conflict { what: "saved LAN operation is absent from the verified directory chain" }`，
该 operation 身份被永久毒化。

修复：改为 `outcome.status != CommitStatus::NotSaved`，prepared-only 操作重新规划并提交，
由 `commit` 自身保证冻结的 prepared 正文与本次尝试一致。

### 缺陷 B：LAN 提交尾部不写投影水位

原闭包只做 `tx.commit()`。目录提交后业务行可见，但
`durability_projection::project_commits_in_transaction` 从未被调用，
`library_projection_watermarks` / `library_applied_operations` 始终为空。
后果：

- `verify_covered_watermark` 与 `validation::validate` 失去水位证据，
  后续追赶无法证明"从哪个提交开始重放"；
- `LibraryProjectionStatus::applied_library_commit_seq` 恒为 0，
  整库已同步判定与只读/待投影状态呈现都读不到真实进度。

修复：闭包内取 `durability.recover(root)` 得到已验证目录链，先
`durability_backfill::verify_covered_watermark`，再
`durability_projection::project_commits_in_transaction(&tx, root, &replay)`，
最后 `tx.commit()`。行与水位因此是同一个原子 SQLite 提交。

## 验证矩阵（5 条，全部装真实 `RootControlPlane`）

其余快照测试都不装控制面，此时 `commit_prepared_projection` 在 `#[cfg(test)]`
下退化成裸 `tx.commit()`，目录优先顺序根本没被测试。本矩阵装真实控制面，
使顺序本身成为被测对象。

| 测试 | 覆盖 |
| --- | --- |
| `snapshot_publishes_the_visible_set_only_through_the_directory` | 非末页纯私有暂存（业务行/游标/目录提交均为 0）；末页发布后 `(2,1,1)`、恰好 1 次目录提交、batch 内含 `echo.sync.peer-cursor.v1` 且 `sequence=12`；新建 SQLite 仅凭该目录重放即得 `(2,1,1,0)` |
| `incremental_page_projects_rows_and_watermark_after_the_directory` | 真实主机发布增量提交 → 接收端 `(1,0,1)`，水位与 `library_applied_operations` 各 1 行；同页重放 `applied=0` 且目录提交仍为 1；新库重放得到 1 首歌 |
| `snapshot_commit_faults_recover_with_one_operation_and_no_partial_set` | `prepared`/`committed` 两个发布窗口分别注入故障：均无可见行与游标；`committed` 故障返回 `library_saved_pending_recovery`；恢复后重试同一页得到 `(0,1,1)`、目录提交仍为 1、水位 1 行 |
| `discarded_snapshot_leaves_no_directory_operation_and_allows_a_fresh_one` | 取消半收快照：session/page/可见行/目录提交全部归零，随后全新快照可正常提交 |
| `snapshot_keeps_metadata_only_favorite_and_empty_playlist_through_the_directory` | metadata-only 喜欢、空歌单、`SongAlias`、`PlaylistMemberAlias` 均进入目录 batch；`playlist_songs=0` 不伪造成员；alias 以 `StateKind::Alias` 保留 |

## 未在本项内解决（转 7.4）

新库重放后 `sync_peer_cursors` 为 0：对端游标以 `StateKind::Cursor` 形式完整保留在目录，
但 `durability_projection/sync_state/related.rs:17-26` 对
`StateTarget::PeerCursor` 返回 `RequiresStateRecovery`，重放时记为未解析而非恢复。
这是 7.4 的既有缺口（远端资源位置声明与完成凭据同样走这条路径），
本项只断言"证据被保留而非丢失"，不声称游标已恢复。
