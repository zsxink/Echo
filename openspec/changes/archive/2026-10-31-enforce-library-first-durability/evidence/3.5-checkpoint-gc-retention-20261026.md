# 3.5 安全 checkpoint/压缩/GC 与引用保护

日期：2026-10-26
分支：`codex/issue-72-library-first-durability`

## 1. 回收顺序与上限（已有实现，本轮补证据）

`durability/checkpoint.rs::compact` 固定顺序：合并覆盖镜像 → 发布 record/state/
resource 三份快照 → 为每个被覆盖提交写不可变 receipt（已存在则重刷，摘要不符即
拒绝）→ 发布并刷盘 ANCHOR → 重读材料化 checkpoint → `snapshot::collect` 清理过期
快照叶 → `cleanup_covered` 回收 journal。

`cleanup_covered` 在任何删除之前完成全部证明：

1. 校验 ANCHOR 的 `library_commit_seq` 等于本次压缩水位，否则
   `cannot collect without matching coverage checkpoint`；
2. 逐条确认 receipt 存在，缺失时 `cannot collect transaction without receipt`；
3. `coverage_gc` / `receipt_gc` 重新刷盘根文件与每份 receipt，并把全部祖先目录记入
   `DirectorySyncSet`，统一 `gc_proof` 一次性同步；
4. 以上全部成功后才 `remove_file(prepared.json)`、`remove_file(committed.json)`、
   `remove_dir`（仅删空目录，未知证据保留并阻断写入）。

链长度只与活跃窗口有关：每 `WINDOW = 32` 个活跃提交压缩，`chain()` 在
`echo/transactions` 超过 `MAX_ACTIVE = 256` 个目录时返回
`active transaction safety limit exceeded`；`transaction::validate` 在写 marker 之前
拒绝，并先用 `preflight_capacity` 校验覆盖聚合与快照尺寸。单份提交/覆盖文件受
`LIMIT = 128 MiB` 读取上限约束。

## 2. 引用图保护

GC 的删除面只有三类：过期快照叶（`snapshot:*` 引用根之外的旧叶）、被覆盖的
journal 文件（`prepared.json`/`committed.json`）、以及删除后为空的
`echo/transactions/<id>/` 目录。**没有任何代码路径删除 `echo/media/`、
`echo/assets/`、`echo/tmp/` 下的字节**；`remove_file` 只出现在发布临时文件、
过期快照叶、被覆盖 journal、以及 `PlaybackRetry` 的临时分片。

因此候选、冲突、删除意图、未完成发布与受管媒体版本天然受保护，它们的声明同时
存在于三处：覆盖镜像的 `resources`、不可变 receipt 的 `batch.resources`、以及
材料化 checkpoint 的 files 映射。journal 被回收后，全新 SQLite 仍可从
`resources` 恢复 `relative_path/content_hash/byte_length`。

## 3. 本轮新增证据（`durability/tests/retention.rs`）

| 测试 | 验证的规格条款 |
| --- | --- |
| `library_durability_active_transaction_limit_refuses_writes_without_removing_bytes` | 超上限时 `chain()` 报明确错误（非静默截断）；写入在 marker 之前被拒，已保存 journal 与 payload 原样保留；清掉多余崩溃目录后同一 batch 以新身份成功提交 |
| `library_durability_interrupted_between_prepared_and_marker_removal_keeps_the_receipt` | 在 `gc:remove` 每一步注入失败（删 prepared 后/删 marker 后），重启从锚点重做；任何时候都满足"marker 只在 redo 之后移除"；只剩下 receipt 时 `read_operation` 仍返回冻结的原始 `LibraryCommit`（含全部资源声明）；恢复后链头为 3、`echo/transactions` 清空、asset 字节完好 |
| `library_durability_collection_never_removes_media_assets_or_staging_bytes` | 构造含受管媒体版本、内容寻址 asset、未完成发布 staging 与 5 类私有 state（Pending/Conflict/DeleteIntent/ResourceLocation/Receipt）的集合，再追加 `WINDOW` 条提交迫使压缩；断言回收后 `media/`/`assets/`/`tmp/` 文件集合逐项不变、每个被引用 state 仍在覆盖镜像中、`read_operation` 仍返回原 batch；用回收后的目录镜像重建全新 SQLite，两份资源声明都能读回，且 `echo/tmp/` 从不被当作资源来源 |

`seeded_collection` 的 state 载荷带 `original_resource`/`asset`，模拟候选、冲突、
删除意图对资源的引用；测试同时确认这些 state 不会因为 journal 回收而从可恢复
镜像消失。

## 5. 边界

- 测试用真实临时目录与注入 hook，覆盖 POSIX 语义；Windows/Linux 原生认证仍属 9.3。
- 本轮不新增资源删除能力，也不把"引用计数"写进 GC：保护来自"从不删除字节"，
  未来若引入媒体回收，必须先建立显式引用图，不能复用当前 journal 回收路径。
- `docs/library-durability-protocol.md` 已同步回收顺序与"GC 不删媒体/assets/staging
  字节"的承诺，并说明超上限时调用方必须让活跃后缀完成压缩。
